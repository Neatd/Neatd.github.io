## 1. 이 활동을 관통하는 질문

키-밸류 저장소에 `Put(key, value)`를 호출하면 데이터는 어디로 갈까? 호출이 성공한 직후 프로세스가 종료되면 복구할 수 있을까? 디스크에 기록하기 전 메모리에서 값이 바뀌었다면 저장소는 이를 알아챌 수 있을까?

LevelDB·RocksDB 스터디와 연구를 통해 살펴본 것은 **데이터가 지나가는 경로, 그 경로의 비용, 그리고 각 구간에서 제공하는 안정성**이었다.

활동은 크게 두 부분이다.

| 구분 | 내용 | 나의 참여 |
| --- | --- | --- |
| LevelDB 스터디·위키 | 내부 구조 분석, 벤치마크, YCSB 튜닝 결과 문서화 | WAL/Manifest 팀 참여, WAL 관련 분석·실험 정리 |
| RocksDB 논문 | 키-밸류 단위 체크섬의 쓰기·복구 경로와 성능 비용 분석 | 「RocksDB의 키-밸류 체크섬 분석」 2저자 |

이 글에서는 먼저 LSM-Tree와 WAL을 정리한 뒤, 내가 위키에 추가한 `max_total_wal_size` 실험, 팀 단위 튜닝·장애 실험, 논문의 체크섬 분석을 연결한다.

## 2. 먼저 구분할 것: 복구 가능성과 손상 탐지

‘데이터가 안전하다’는 말에는 다른 문제가 섞여 있다.

| 질문 | 관련 메커니즘 |
| --- | --- |
| 메모리에만 있던 변경을 재시작 후 복원할 수 있는가? | WAL과 복구 절차 |
| 성공 응답한 쓰기가 정전 후에도 남는가? | WAL 설정과 동기화·영속성 조건 |
| 기록·복사·보관 중 데이터가 바뀌었는가? | 체크섬과 검증 범위 |
| 손상을 발견한 뒤 올바른 값으로 되돌릴 수 있는가? | 정상 복제본·백업 등 별도의 복구 수단 |

WAL은 재실행할 기록을 남긴다. 체크섬은 데이터가 변했는지를 검사한다. **체크섬이 있다고 데이터가 영구 저장되는 것은 아니고, 손상을 탐지했다고 원래 값이 자동으로 복원되는 것도 아니다.**

이 구분을 해 두면 뒤에 나오는 옵션과 실험 결과를 훨씬 정확하게 읽을 수 있다.

## 3. LevelDB·RocksDB의 큰 그림

LevelDB는 키-밸류 저장소이고, RocksDB는 이를 기반으로 발전한 저장소다. 둘 다 LSM 계열 구조를 이해하는 데 좋은 분석 대상이지만 기능과 옵션이 동일하지는 않다.

예를 들어 이 스터디의 WAL 활성·비활성 비교는 RocksDB로 수행했다. 기본 LevelDB API에 같은 WAL 비활성 옵션이 있다고 생각하면 실험 대상을 혼동하게 된다.

### 3.1 LSM-Tree의 쓰기 흐름

개념적으로 다음과 같이 이해할 수 있다.

```text
사용자의 쓰기 요청
      ↓
WriteBatch 구성
      ↓
WAL 기록 ──────────────→ 재시작 시 복구에 사용
      ↓
MemTable에 반영
      ↓
MemTable 교체·불변 상태로 전환
      ↓
Flush: SSTable 생성
      ↓
Compaction: SSTable들을 읽고 병합·재작성
```

위 흐름은 일반적인 WAL 사용 쓰기 경로를 이해하기 위한 도식이다. RocksDB에서 WAL을 끄거나 다른 쓰기 옵션을 사용하면 세부 경로가 달라진다.

| 구성 요소 | 역할 |
| --- | --- |
| WriteBatch | 하나 이상의 변경 작업을 묶어 표현 |
| WAL | 아직 SSTable에 반영되지 않은 변경의 복구 기록 |
| MemTable | 메모리 안에서 최근 변경을 관리 |
| Immutable MemTable | 새 쓰기 입력을 받지 않고 디스크 반영을 기다리는 메모리 구조 |
| SSTable | 정렬된 데이터를 담은 저장 파일 |
| Compaction | 파일 병합, 버전 정리, 공간 회수 등을 수행하는 작업 |
| MANIFEST | 어떤 파일과 버전 상태가 현재 DB를 구성하는지 나타내는 메타데이터 기록 |

WAL이 사용자 변경을 복구하기 위한 기록이라면, MANIFEST는 저장소의 파일·버전 구성을 관리한다. 비슷한 로그 형식을 사용하더라도 담는 내용과 역할은 다르다.

### 3.2 왜 쓰기에 유리하다고 할까?

LSM 계열은 매번 디스크의 해당 위치를 찾아 값을 고치는 대신, 메모리에 변경을 모으고 로그와 정렬 파일을 생성하는 방식을 활용한다. 이를 통해 쓰기를 모아서 처리할 여지가 생긴다.

대신 데이터가 이후 Compaction에서 다시 쓰일 수 있다. 여러 파일을 찾아 읽거나 병합해야 하는 비용도 발생한다.

따라서 ‘Append-only라서 언제나 B-Tree보다 빠르다’고 외우기보다는 다음 질문으로 이해하는 편이 좋다.

- 변경을 어느 시점에 모아서 기록하는가?
- 나중에 병합하면서 얼마나 다시 읽고 쓰는가?
- 현재 워크로드는 읽기·쓰기·범위 탐색 중 무엇이 많은가?
- 메모리, 압축, 캐시, 저장장치 조건은 어떠한가?

## 4. WAL 파일을 코드로 읽기

WAL/Manifest 팀 문서에서는 로그 형식과 `log::Writer`, `log::Reader`, 파일 I/O 경로를 분석했다. 아래 설명은 해당 스터디와 LevelDB 1.23 소스를 함께 기준으로 정리한 것이다.

### 4.1 논리 레코드와 물리 조각

하나의 논리 레코드가 파일 블록 경계 안에 모두 들어가지 않을 수 있다. 이때 기록기는 논리 레코드를 여러 물리 조각으로 나눈다.

LevelDB 로그의 블록 크기는 **32KiB, 즉 32,768바이트**다. 각 물리 레코드에는 7바이트 헤더가 붙는다.

```text
물리 레코드 헤더
┌──────────────┬──────────────┬───────────┐
│ CRC32C 4B    │ 길이 2B      │ 타입 1B   │
└──────────────┴──────────────┴───────────┘
그 뒤에 payload가 이어짐
```

CRC32C는 타입과 데이터에 대해 계산하며, 저장할 때 마스킹한다. 이 형식은 **LevelDB 로그 형식**에 대한 설명이다. RocksDB의 여러 WAL 형식까지 모두 같은 헤더라고 일반화하지 않는다.

| 타입 | 의미 |
| --- | --- |
| `kFullType` | 논리 레코드 전체가 조각 하나에 들어감 |
| `kFirstType` | 나뉜 논리 레코드의 시작 |
| `kMiddleType` | 중간 조각 |
| `kLastType` | 마지막 조각 |

```text
작은 레코드: FULL
큰 레코드:   FIRST → MIDDLE → ... → LAST
```

여기서 블록과 조각은 같은 단위가 아니다. 하나의 블록에 여러 물리 레코드가 들어갈 수 있다. 마지막에 헤더조차 들어갈 공간이 없으면 남은 부분을 패딩하고 다음 블록으로 넘어간다.

### 4.2 Writer::AddRecord와 EmitPhysicalRecord

`AddRecord()`는 입력 레코드를 현재 블록의 남은 공간에 맞게 나누고, 조각이 시작·중간·끝 중 어디에 해당하는지 정한다.

`EmitPhysicalRecord()`는 헤더와 CRC를 구성하고 실제 데이터 출력을 요청한다.

```text
AddRecord
  → 블록의 남은 공간 계산
  → 필요한 길이만큼 조각 분리
  → FULL / FIRST / MIDDLE / LAST 결정
  → EmitPhysicalRecord
       → 헤더와 CRC 구성
       → 헤더 Append
       → payload Append
       → Flush
```

여기서 `Flush()`가 보인다고 곧바로 정전에 견디는 디스크 동기화까지 끝났다고 해석하면 안 된다. 파일 객체의 버퍼를 비우는 것과 영속 저장을 위한 `Sync()`는 구분해야 한다.

### 4.3 Reader::ReadRecord는 상태를 관리하며 재조립한다

읽기 경로에서는 `ReadPhysicalRecord()`가 물리 조각과 오류 상태를 반환하고, `ReadRecord()`가 논리 레코드를 완성한다.

`scratch`는 여러 조각을 모으는 버퍼다. `in_fragmented_record`는 현재 나뉜 레코드를 읽고 있는지를 나타낸다.

| 반환 타입·상태 | 핵심 처리 |
| --- | --- |
| `kFullType` | 전체 레코드를 반환 |
| `kFirstType` | `scratch`를 시작 조각으로 설정하고 조립 상태 시작 |
| `kMiddleType` | 조립 중이라면 `scratch`에 추가, 시작이 없으면 오류 보고 |
| `kLastType` | 마지막 조각을 추가하고 완성된 레코드 반환 |
| `kEof` | 읽기 종료. 끝나지 않은 논리 레코드는 반환하지 않음 |
| `kBadRecord` | 손상 상태에 따라 조립 데이터를 버리고 오류 처리 |

중요한 것은 **중간에 끊긴 조각을 정상 레코드처럼 반환하지 않는 것**이다. 끝부분의 불완전 레코드는 기록 도중 프로세스가 종료된 결과일 수 있으므로, 파일 내부의 일반적인 손상과 똑같이 처리하지 않는 경우도 있다.

`ReadPhysicalRecord()`에서는 길이 범위, 읽기 결과, 설정된 경우 CRC 등을 확인한다. `kEof`, `kBadRecord`는 파일에 기록되는 네 가지 조각 타입과 구별되는 판독기의 내부 상태다.

[LevelDB 로그 형식](https://github.com/google/leveldb/blob/1.23/doc/log_format.md), [Writer 소스](https://github.com/google/leveldb/blob/1.23/db/log_writer.cc), [Reader 소스](https://github.com/google/leveldb/blob/1.23/db/log_reader.cc)를 함께 보면 기록과 복구를 한 쌍으로 이해할 수 있다.

## 5. WAL, Flush, Sync를 구분하기

같은 ‘쓰기 완료’라도 어디까지 데이터가 도달했는지 다를 수 있다.

```text
애플리케이션의 WAL 버퍼
       ↓ WAL flush
OS 버퍼·페이지 캐시
       ↓ sync
영속 저장장치
```

여기에 별도의 경로가 하나 더 있다.

```text
MemTable ── MemTable flush ──→ SSTable
```

**WAL flush와 MemTable flush는 같은 작업이 아니다.** 이 둘을 섞으면 성능과 장애 실험의 결과를 잘못 설명하게 된다.

### 5.1 주요 옵션의 의미

| 옵션·API | 의미 |
| --- | --- |
| `disableWAL` | 쓰기에 WAL을 사용할지 여부. 벤치마크 플래그 표기는 도구에 따라 다를 수 있음 |
| `manual_wal_flush = false` | 기본적인 자동 WAL flush 사용 |
| `manual_wal_flush = true` | 매 쓰기 후 자동 WAL flush를 끄고 수동 제어 사용 |
| `FlushWAL(false)` | WAL 버퍼를 내보내되 이 호출로 영속 동기화까지 요청하지는 않음 |
| `FlushWAL(true)` | WAL flush와 동기화를 요청 |
| `WriteOptions::sync = true` | 쓰기의 동기화를 요청 |

공식 문서는 OS 버퍼에 도달한 데이터가 애플리케이션 프로세스 종료에는 남을 수 있지만, 아직 영속 저장이 끝난 것은 아니라고 설명한다. `manual_wal_flush=true`가 그 자체로 더 안전한 설정이라는 뜻은 아니다. [RocksDB 공식 FlushWAL 설명](https://rocksdb.org/blog/2017/08/25/flushwal.html)

### 5.2 프로세스 종료 실험과 정전 실험은 다르다

| 장애 | 잃을 수 있는 상태 | 실험 해석 |
| --- | --- | --- |
| 프로세스 종료 | 해당 프로세스의 메모리·미배출 버퍼 | OS가 계속 동작하면 페이지 캐시는 남을 수 있음 |
| OS 장애·정전 | 휘발성 OS 버퍼까지 포함 | 프로세스 종료 실험만으로 보존 여부를 입증할 수 없음 |

따라서 ‘WAL을 켰더니 종료 후 데이터를 모두 읽었다’는 결과는 그 실험 조건에서의 관찰이다. 모든 장애에서 무손실을 보장하는 문장으로 바꾸어서는 안 된다.

## 6. 내가 위키에 정리한 max_total_wal_size 실험

개인 기여가 변경 이력으로 확인되는 문서는 `max_total_wal_size` 실험이다. [내 PR #16](https://github.com/DKU-StarLab/leveldb-wiki/pull/16)은 해당 실험의 가설·설계·결과·논의를 추가한 기록이며, 현재는 [WAL 벤치마크 문서](https://github.com/DKU-StarLab/leveldb-wiki/blob/main/benchmarks/wal_2.md)에서 내용을 볼 수 있다.

### 6.1 질문: WAL 크기 제한을 줄이면 성능이 달라질까?

RocksDB의 Column Family는 논리적으로 데이터를 나누는 단위다. 각 Column Family는 자신의 MemTable·SST 상태를 관리하지만 WAL은 공유한다.

어떤 Column Family의 데이터가 아직 MemTable에 남아 있다면 그 데이터를 복구하기 위한 WAL을 계속 보관해야 할 수 있다.

```text
여러 Column Family가 WAL 공유
       ↓
오래된 WAL에 의존하는 MemTable이 남아 있음
       ↓
WAL 정리 지연
       ↓
전체 WAL 크기 한도를 넘으면 관련 Column Family flush 유도
```

`max_total_wal_size`는 이 관계를 제어하는 옵션이다. 아직 필요한 WAL을 먼저 지워서 크기만 맞추는 설정으로 이해하면 안 된다.

내 가설은 **한도가 작아지면 flush가 더 자주 유도되어 성능에 영향을 줄 수 있다**는 것이었다.

### 6.2 처음에는 뚜렷한 차이가 보이지 않았다

문서에 남긴 실험은 `fillseq`, 10,000,000개 항목 쓰기를 기준으로 옵션 값을 바꾸는 방식이었다. 환경은 macOS Monterey, 2.3GHz 8코어 Intel Core i9, Apple SSD AP1024N 1TB였다.

그런데 처음 실험에서는 유의미한 차이를 확인하지 못했다. 이후 옵션 설명을 살펴보며 중요한 조건을 확인했다.

1. `0`은 한도가 0바이트라는 뜻이 아니라 **자동 계산**을 뜻한다.
2. 해당 버전의 설명에서 이 옵션은 **여러 Column Family가 있는 경우**를 대상으로 한다.
3. 단일 Column Family에서는 WAL 크기가 MemTable 크기와 flush 조건에 좌우되어 옵션 효과가 다르게 나타날 수 있다.

즉, 옵션 값만 바꾸는 것으로 충분하지 않았다. **효과가 나타나는 구조와 조건을 먼저 만들어야 했다.**

### 6.3 기본값을 계산하고 여러 Column Family로 확장

RocksDB 7.8.3의 옵션 설명은 자동 한도를 다음과 같이 정의한다.

```text
자동 WAL 크기 한도
= 4 × Σ(각 Column Family의 write_buffer_size × max_write_buffer_number)
```

예를 들어 각 Column Family에 64MiB 버퍼를 최대 2개 사용하는 동일 조건이라면 다음과 같다.

| Column Family 수 | 계산 | 자동 한도 |
| --- | --- | ---: |
| 10 | 10 × 64MiB × 2 × 4 | 5,120MiB = 5GiB |
| 15 | 15 × 64MiB × 2 × 4 | 7,680MiB = 7.5GiB |

과거 문서의 MB·GB 표기는 바이트 단위가 섞일 여지가 있어 여기서는 MiB·GiB로 기준을 명시했다. [RocksDB 7.8.3 옵션 정의](https://github.com/meta/rocksdb/blob/v7.8.3/include/rocksdb/options.h)

이후 Column Family를 10개·15개로 늘리고 WAL 한도를 조정했다. 한도를 고정한 상태에서 Column Family 수를 바꾸는 조건도 검토했다.

### 6.4 관찰과 한계

문서에는 작은 한도에서 성능이 나빠지는 듯한 경향, 일부 작은 값에서 `Too many open file`로 벤치마크가 실패한 상황 등이 기록되어 있다.

다만 당시 기록에는 실제 Column Family별 작업 분배와 출력 결과의 집계 범위를 확실히 검증하지 못한 부분도 있다. 실패 원인 역시 파일 디스크립터 수와 flush 통계를 충분히 측정한 인과 분석은 아니었다.

따라서 이 실험의 결과는 ‘보편적인 최적 WAL 한도를 찾았다’보다 다음과 같이 정리하는 것이 정확하다.

> 옵션의 적용 조건과 기본값 의미를 확인했고, 다중 Column Family에서의 WAL 공유·flush 관계를 실험으로 탐색했다. 정량적 결론을 강화하려면 실제 작업 분배, flush 횟수, 파일 수와 반복 측정이 더 필요하다.

이 과정에서 배운 것은 결과가 예상과 다를 때 **실험 대상이 정말 가설을 검증하고 있는지**부터 확인해야 한다는 점이었다.

## 8. 팀 스터디의 튜닝·장애 실험에서 배운 것

### 8.1 YCSB 튜닝: 워크로드마다 좋은 설정이 다르다

팀은 YCSB-cpp로 LevelDB 설정을 비교했다. 레코드 수와 작업 수는 각각 2,000,000개였고, Load A → Run A → Run B → Run D 순서로 실행했다.

| 워크로드 | 주요 구성 |
| --- | --- |
| A | 읽기 50% + 업데이트 50% |
| B | 읽기 95% + 업데이트 5% |
| D | 읽기 95% + 삽입 5%, 최신 항목 중심 접근 |

특히 D를 단순히 ‘B와 같은 읽기·수정 비율’로 설명하면 삽입과 접근 분포의 차이를 놓치게 된다.

WAL/Manifest 팀 설정과 보고된 처리량은 다음과 같다.

| 설정 | 팀 선택값 |
| --- | --- |
| Write Buffer | 128MB |
| 최대 파일 크기 | 64MB |
| Block Cache | 128MB |
| Block Size | 8KB |
| 압축 | Snappy |
| Bloom Filter | 10 bits/key |
| Block Restart Interval | 16 |

| 단계 | 평균 처리량, ops/sec |
| --- | ---: |
| Load A | 71,065 |
| Run A | 73,928 |
| Run B | 131,709 |
| Run D | 191,939 |

이는 **팀 단위의 특정 대회 조건 결과**다. WAL/Manifest 팀은 Run A에서 가장 높은 처리량을 기록했지만 모든 워크로드에서 최고였던 것은 아니다. 또 기본 설정 대비 개선율을 이 표만으로 계산할 수는 없다.

설정값을 그대로 모든 서비스의 권장값으로 사용하기보다는, 읽기·쓰기 비율과 키 분포, 데이터 크기, 메모리 제약이 달라질 때 결과가 어떻게 바뀌는지 봐야 한다. [스터디 튜닝 조건과 결과](https://github.com/DKU-StarLab/leveldb-study/blob/main/tuning/README.md)

### 8.2 네 가지 장애 시나리오의 범위

팀 WAL 문서에는 WAL 사용 여부와 수동 MemTable flush 여부를 조합한 종료 실험도 정리되어 있다.

| 시나리오 | WAL | 수동 MemTable flush | 당시 보고된 관찰 |
| --- | --- | --- | --- |
| 1 | 끔 | 없음 | 아직 flush하지 않은 메모리 데이터 손실 |
| 2 | 끔 | 있음 | 마지막 flush 뒤의 일부 데이터 손실 가능 |
| 3 | 켬 | 없음 | 해당 프로세스 종료 실험에서 데이터 보존 |
| 4 | 켬 | 있음 | 해당 프로세스 종료 실험에서 데이터 보존 |

이 실험의 코드 링크는 다른 팀원의 저장소로 연결된다. 팀의 학습 결과로 참고하되, 내가 이 코드를 단독 작성했다고 설명하지 않는다.

또한 문서의 종료 조건은 Ctrl+C/SIGINT를 이용한 프로세스 종료다. 정전이나 OS 장애까지 검증한 실험은 아니다. 네 가지 시나리오에서 말하는 수동 flush와 `manual_wal_flush` 옵션도 구별해야 한다.

## 9. 논문으로 이어진 질문: 디스크에 쓰기 전 손상은?

논문 「RocksDB의 키-밸류 체크섬 분석」은 2022 한국소프트웨어종합학술대회 논문집에 실린 연구이며, 나는 2저자로 참여했다. 저자는 신수환, 박세연, 최민국, 유시환, 최종무 순이다.

주요 질문은 다음과 같다.

> WAL과 SST 파일에 체크섬이 있어도, 사용자 버퍼에서 WriteBatch와 MemTable로 데이터가 이동하는 동안 생긴 손상을 잡을 수 있을까? 보호를 추가하면 비용은 얼마나 들까?

### 9.1 파일 체크섬만으로 부족할 수 있는 이유

데이터가 메모리에서 먼저 잘못 바뀐 뒤, 그 잘못된 데이터를 기준으로 디스크 체크섬을 계산했다고 생각해 보자.

```text
정상 데이터 A
   ↓ 메모리 손상
잘못된 데이터 B
   ↓ B의 체크섬을 생성해 함께 저장
저장 데이터 B와 그 체크섬은 서로 일치
```

나중에 디스크 체크섬을 검사해도 ‘디스크에 저장된 뒤 바뀌지 않았다’는 사실만 확인할 수 있다. 사용자 입력 A가 유지되었는지까지는 알 수 없다.

따라서 보호를 시작하는 위치와 검증을 끝내는 위치가 중요하다. 이 논문은 기존 RocksDB의 **per key-value checksum 기능을 분석·실험**한 연구다. 해당 기능이나 XXH3 알고리즘 자체를 새로 발명한 연구는 아니다.

## 10. Protection Info: 무엇을 함께 보호하나?

키와 값만 아니라 작업 타입과 내부 메타데이터도 보호 대상에 포함된다. 논문 Figure 3의 구조를 개념적으로 풀면 다음과 같다.

```text
WriteBatch 보호정보
= H_key(key)
  XOR H_value(value)
  XOR H_type(operation type)
  XOR H_cf(column family ID)

MemTable 보호정보
= H_key(key)
  XOR H_value(value)
  XOR H_type(operation type)
  XOR H_seq(sequence number)
```

`H_*`는 각 구성 요소에 대한 XXH3 기반 해시를 나타내는 설명용 표기다. 실제 구현의 필드별 시드와 인코딩까지 재현한 코드는 아니다.

| 정보 | 포함하는 이유 |
| --- | --- |
| Key·Value | 저장할 데이터 자체를 보호 |
| Operation Type | 값 저장·삭제 등 작업 의미의 변경을 탐지 |
| Column Family ID | WriteBatch에서 어느 논리 공간에 속하는지 보호 |
| Sequence Number | MemTable에 반영되는 순서·버전 정보 보호 |

MemTable은 특정 Column Family에 속하므로 같은 방식으로 ID를 들고 있을 필요가 없고, 대신 시퀀스 정보가 중요해진다.

### 10.1 XOR를 사용하는 이유

XOR에는 같은 값을 두 번 적용하면 없어지는 성질이 있다.

```text
A XOR B XOR B = A
```

따라서 WriteBatch 보호정보에서 Column Family 해시를 XOR해 제거하고 시퀀스 해시를 더하면, 키와 값 전체를 다시 해시하지 않고 다른 표현의 보호정보로 변환할 수 있다.

큰 키·값을 재계산하는 비용을 줄이는 아이디어다. 단, 해시는 충돌 가능성이 있는 검사 수단이며 암호학적 진위 보장과 같지 않다. 공격자가 의도적으로 조작하는 상황까지 모두 막는다는 주장은 하지 않는다.

## 11. 쓰기 경로에서 체크섬은 언제 검사하나?

논문 Section 2.2는 다음 경로를 설명한다.

```text
사용자 버퍼
  → 보호정보 생성
  → WriteBatch로 데이터 복사
  → WriteBatch 내용과 보호정보 검증
       ├─ WAL 기록: fragment별 CRC32C로 보호 전달
       └─ MemTable 삽입: 엔트리 버퍼로 복사한 데이터 검증
```

핵심은 디스크에 기록하는 순간만 검사하는 것이 아니라, **메모리 사이 복사된 결과를 앞서 만든 보호정보와 비교한다**는 점이다.

CRC32C와 XXH3도 역할을 나누어 이해해야 한다.

| 검사 | 이 연구에서 중심적으로 다루는 범위 |
| --- | --- |
| WAL fragment의 CRC32C | 저장된 조각을 읽고 손상 여부 확인 |
| 키-밸류 보호정보 | 키·값·메타데이터의 메모리 경로 확인 |
| 복구 중 XXH3 스트리밍 해시 | 조각을 합치고 WriteBatch로 복사하는 경계 확인 |

‘XXH3가 CRC32C를 전부 대체한다’는 구조가 아니다.

## 12. 복구 경로의 Checksum Handshake

재시작 후에는 WAL 조각을 읽어 논리 레코드로 합친 다음 WriteBatch를 만들고 MemTable을 복원한다.

문제는 보호정보를 만드는 시점이다. 이미 잘못 복사된 내용을 기준으로 새 보호정보를 만들면 잘못된 데이터와 보호정보가 서로 일치할 수 있다.

논문 Figure 5는 이 경계를 다음과 같이 연결한다.

1. WAL fragment를 읽을 때 CRC32C를 검증한다.
2. fragment를 이용해 XXH3 스트리밍 해시 상태를 갱신한다.
3. fragment들을 연결해 WAL 논리 레코드를 구성한다.
4. 레코드를 WriteBatch로 복사하고 키-밸류 보호정보를 생성한다.
5. 스트리밍 해시와 WriteBatch 내용의 해시를 비교한다.

```text
검증된 WAL fragment들 ──→ 스트리밍 해시
          │                       │
          └─ 레코드 구성·복사 ─→ WriteBatch
                                  │
                     두 경로의 체크섬 비교
                                  ↓
                   이후 키-밸류 보호정보로 검증 계속
```

여기서 handshake는 네트워크 연결 협상이 아니라, **데이터 표현이 바뀌는 경계에서 검사를 이어 주는 과정**이다.

각 단계의 검사가 서로 독립된 섬처럼 끝나는 것이 아니라, ‘새 보호정보를 믿어도 되는가’를 이전 단계와 연결한다는 점이 중요하다.

## 13. 체크섬 성능 실험: 보호 범위를 늘리면 얼마가 드나?

### 13.1 실험 조건

논문은 체크섬을 켜고 끌 때의 처리량을 비교했다. 실험에서 보호정보를 활성화한 경우 크기는 8바이트로 통일했다.

| 항목 | 논문 보고값 |
| --- | --- |
| OS | Ubuntu 18.04 |
| CPU | Intel Core i7-10700K, 3.80GHz |
| RAM | 16GB |
| SSD | Samsung SSD 970 EVO 1TB |
| RocksDB | 7.8 |

논문은 WriteBatch 보호정보 크기로 0·8바이트, MemTable은 0·1·2·4·8바이트를 지원한다고 설명한다. 0은 비활성 상태다. 아래 비교는 양쪽 활성 조건을 8바이트로 맞춘 결과다.

| 비교 조건 | WriteBatch 검사 | MemTable 검사 |
| --- | --- | --- |
| 기준 | 끔 | 끔 |
| 조건 1 | 끔 | 켬 |
| 조건 2 | 켬 | 끔 |
| 조건 3 | 켬 | 켬 |

### 13.2 주요 결과

논문 Figure 6과 Section 3.3에서는 다음 결과를 보고한다.

- 체크섬을 적용할수록 처리량이 감소했다.
- 해당 조건에서 WriteBatch 체크섬의 오버헤드가 MemTable 체크섬보다 컸다.
- 두 체크섬을 모두 적용하면 미적용 대비 **약 10% 오버헤드**가 발생했다.

이는 해당 벤치마크와 버전·환경에서 보고한 결과다. 모든 워크로드에서 처리량이 정확히 10% 감소하거나, 지연 시간이 정확히 10% 증가한다는 뜻은 아니다.

그래프에는 정밀한 수치 표가 없으므로 막대 높이에서 읽은 근삿값을 정확한 측정값처럼 다시 쓰지는 않았다. 또한 논문에 명시된 정보만으로 키·값 크기, 반복 횟수, 분산을 포함한 전체 실험을 그대로 재현하기에는 정보가 더 필요하다.

### 13.3 이 결과가 말해 주는 것

체크섬 비용에는 해시 계산, 보호정보 저장, 추가 메모리 접근과 검증 등이 포함될 수 있다. 그러나 전체 처리량 그래프만으로 그중 어느 것이 병목인지까지 확정할 수는 없다.

‘CPU와 디스크 비용을 분리해 원인을 입증했다’고 주장하려면 프로파일링과 별도의 통제 실험이 필요하다. 이 논문에서 직접 확인한 것은 **검사 위치별 활성·비활성에 따른 처리량 차이**다.

## 14. 보호 범위는 버전과 경로를 붙여 말하기

논문은 당시 per key-value checksum이 사용자 쓰기부터 MemTable 삽입까지의 보호와 복구 경로를 다룬다고 설명한다. Flush·Compaction·사용자 읽기로 해당 보호를 확장하는 일은 향후 방향으로 제시했다.

이를 ‘RocksDB의 읽기나 SST 파일에는 체크섬이 전혀 없다’고 해석하면 틀린다. 기존 블록·파일 검사와 여기서 분석한 키-밸류 단위 보호는 별개의 층이다.

또한 이 글은 **2022년 논문과 RocksDB 7.8 환경**을 중심으로 정리한 것이다. 현재 버전에도 같은 한계가 그대로 남아 있다고 단정하지 않는다.

## 15. 개인 기여와 팀 성과를 구분해서 정리하기

| 범위 | 설명 |
| --- | --- |
| 개인 활동 | WAL/Manifest 파트 스터디·문서화 참여, `max_total_wal_size` 실험의 위키 추가 |
| 팀 활동 | WAL 로그 경로 분석, 옵션 벤치마크, YCSB 튜닝 결과 정리 |
| 팀의 참고 실험 | WAL·수동 flush 조합에 따른 프로세스 종료 실험. 코드는 다른 팀원 저장소에 연결 |
| 공동 연구 | RocksDB per key-value checksum의 경로·성능 분석 논문 2저자 참여 |

내가 이 활동을 통해 키운 역량은 함수 이름을 나열하는 것이 아니라, **옵션 → 내부 동작 → 관찰 지표 → 해석의 한계**를 연결하는 것이었다.

특히 `max_total_wal_size` 실험에서는 옵션의 기본값이 겉보기 숫자와 다를 수 있고, 효과가 나타나는 전제 조건을 놓치면 실험을 반복해도 원인을 설명하기 어렵다는 점을 배웠다.

체크섬 연구에서는 ‘검사를 한다’는 사실보다 **무엇을 기준으로 어느 경계까지 검사하는지**가 중요하다는 점을 이해했다. 손상된 데이터로 새 체크섬을 만들면 검사가 통과할 수 있다는 문제는 저장소 밖의 데이터 파이프라인에서도 생각해 볼 만한 관점이다.

## 16. 다시 실험한다면 더 확인할 것

다음은 기존 성과와 별도로 생각한 후속 검증 항목이다.

| 영역 | 추가로 확인할 내용 |
| --- | --- |
| WAL 한도 | 실제 Column Family별 쓰기량, live WAL 크기, flush 횟수·바이트 |
| 파일 오류 | 열린 파일 수, 파일 디스크립터 한도, 실패 시점의 로그 |
| 장애 복구 | 성공 응답한 쓰기 목록과 복구 결과 비교, 프로세스·OS 장애 구분 |
| 체크섬 | 키·값 크기, batch 크기, 스레드 수별 처리량과 지연 분포 |
| 병목 | CPU 프로파일, 해시 실행 시간, 메모리 사용량, I/O 대기 분리 |
| 무결성 | 제어된 손상 주입으로 어느 경계에서 탐지하는지 확인 |
| 재현성 | 정확한 커밋·옵션·실행 명령, 반복 횟수와 분산 저장 |

처리량이 낮아졌다는 사실과 보호가 실제 손상을 잡았다는 사실은 서로 다른 실험으로 확인해야 한다. 평균 처리량뿐 아니라 오류, 꼬리 지연, 복구 시간도 함께 볼 필요가 있다.

## 17. 질문으로 되짚어 보기

### WAL이 있는데 왜 sync가 필요한가?

WAL 기록이 애플리케이션 버퍼나 OS 캐시에만 있을 수 있기 때문이다. 어떤 장애까지 견딜지를 정하고 동기화 조건을 함께 봐야 한다.

### Flush와 Compaction은 같은가?

MemTable flush는 메모리 데이터를 SSTable로 내리는 작업이고, Compaction은 SSTable들을 병합·재작성하는 작업이다. 관련은 있지만 구별해야 한다.

### max_total_wal_size가 0이면 WAL을 못 쓰나?

아니다. 분석한 버전에서는 Column Family의 버퍼 설정에 따라 자동 한도를 계산한다. 0의 의미를 옵션 정의에서 확인해야 한다.

### 왜 여러 Column Family를 확인했나?

MemTable·SST는 각각 관리하면서 WAL은 공유하기 때문이다. 아직 flush하지 않은 Column Family가 오래된 WAL의 정리를 지연시킬 수 있다.

### 체크섬을 끄면 빨라지니 끄는 것이 좋은가?

해당 실험에서 성능 비용은 확인했지만, 꺼도 된다는 보편적 결론은 아니다. 필요한 보호 범위와 오류 비용, 워크로드를 함께 판단해야 한다.

### CRC32C가 있는데 XXH3를 왜 사용하나?

보호하는 대상과 경계가 다르다. WAL 조각의 저장 무결성 검사와 키-밸류의 메모리 이동 검사를 연결한다.

### 논문에서 새 체크섬 알고리즘을 개발했나?

기존 RocksDB의 per key-value checksum을 분석하고 활성 조건별 성능 영향을 실험했다. XXH3나 기능 자체를 새로 개발했다고 설명하지 않는다.

### 나의 기여를 짧게 말하면?

WAL/Manifest 팀에서 저장소 내부 동작을 공부하고 문서화했으며, 다중 Column Family와 WAL 한도 관계를 실험한 내용을 위키에 추가했다. 이후 RocksDB의 키-밸류 체크섬 경로와 비용을 분석하는 논문에 2저자로 참여했다.

## 18. 기억할 핵심

1. **WAL은 복구 기록, sync는 영속화 조건, 체크섬은 손상 검사다.**
2. **WAL flush와 MemTable flush는 다른 작업이다.**
3. **로그는 물리 조각을 완전한 논리 레코드로 재조립해야 한다.**
4. **옵션 효과를 보려면 기본값의 의미와 적용 조건부터 확인해야 한다.**
5. **프로세스 종료에서 보존되었다고 정전까지 검증한 것은 아니다.**
6. **체크섬은 데이터 표현이 바뀌는 경계까지 연결해서 생각해야 한다.**
7. **논문의 약 10%는 특정 조건의 오버헤드이며 보편 상수가 아니다.**
8. **개인 위키 기여, 팀 실험, 공동 논문 성과의 범위를 구분한다.**
