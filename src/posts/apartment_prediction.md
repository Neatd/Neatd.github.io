## 1. 데이터 분석과 실험 구조를 함께 고민한 프로젝트

같은 면적과 비슷한 연식의 아파트라도 어디에 있는지에 따라 전세가는 크게 다르다. 그렇다면 ‘역과 가깝다’, ‘학교가 많다’, ‘주변에 녹지가 있다’는 설명을 모델이 사용할 수 있는 숫자로 어떻게 바꿀 수 있을까?

이번 프로젝트에서는 수도권 아파트의 전세 실거래가를 예측했다. 나는 **EDA와 주요 입지 피처의 설계·구현, 폴드 성능을 활용한 앙상블 실험, 공통 코드 모듈화**에 참여했다.

단순히 모델을 학습하는 것뿐 아니라, 분석에서 나온 가설을 팀원들이 같은 코드로 검증하고 다시 사용할 수 있도록 연결하는 데 시간을 많이 썼다.

| 항목 | 내용 |
| --- | --- |
| 프로젝트 | 수도권 아파트 전세가 예측, Boostcamp AI Tech 7기 Level 2 |
| 팀 | RECSYS-08, RECONOVA, 6명 |
| 기간 | 2024.10.02–2024.10.24 |
| 예측 대상 | 거래별 전세보증금 `deposit` |
| 주요 데이터 | 거래 정보, 아파트 좌표, 지하철·학교·공원, 월별 금리 |
| 주요 평가 | MAE, 보조 지표 RMSE·R² |
| 개인 핵심 기여 | EDA → 입지 피처 → 앙상블 실험 → 공통 실행 구조로 연결 |

팀 회고에는 최종 제출까지 리더보드 1위를 유지했다고 기록되어 있다. 이 글에서는 순위와 함께, 그 결과를 만들기 위해 어떤 분석과 구현을 했는지 정리한다.

## 2. 출발점: 적은 컬럼, 많은 거래

기본 학습 데이터는 약 180만 건이지만 입력 종류는 많지 않았다. 면적, 계약 시점, 층수, 건축 연도, 좌표, 계약 유형 등이 중심이었다.

| 데이터 | 제공하는 정보 | 활용 방향 |
| --- | --- | --- |
| `train.csv`, `test.csv` | 거래·아파트 기본 정보 | 거래별 가격 예측 |
| `subwayInfo.csv` | 지하철역 좌표 | 대중교통 접근성 |
| `schoolinfo.csv` | 학교 좌표·학교급 | 교육시설 접근성·주변 분포 |
| `parkInfo.csv` | 공원 좌표·면적 | 주변 녹지의 규모 |
| `interestRate.csv` | 월별 금리 | 계약 시점의 거시 환경 |

핵심은 행이 많다는 사실만으로 충분한 정보가 주어지지는 않는다는 점이었다. 위도·경도가 있어도 모델이 교통·교육·녹지의 의미까지 직접 아는 것은 아니다. 추가 자료와 결합해 이 정보를 표현할 필요가 있었다.

## 3. EDA: 가설을 세우기 전에 무엇을 확인했나?

EDA는 분포 그림 몇 개를 그리는 단계로 끝내지 않았다. **데이터 품질 → 가격의 기본 관계 → 시간 변화 → 공간 분포 → 외부 정보와의 연결** 순서로 살펴봤다.

### 3.1 결측과 중복은 서로 다른 문제였다

기본 거래 데이터에는 확인한 컬럼 기준으로 결측치가 없었다. 반면 행 식별자인 `index`를 제외하면 같은 내용이 반복되는 거래 행이 있었다.

저장된 EDA 출력에서는 다음과 같이 정리된다.

| 구분 | 행 수 |
| --- | ---: |
| 원본 학습 데이터 | 1,801,228 |
| `index`를 제외하고 중복 제거한 뒤 | 1,717,611 |
| 제거한 행 | 83,617 |
| 테스트 데이터 | 150,172 |

여기서 중복 제거는 모델이 같은 기록을 반복해서 학습하는 문제를 줄이려는 전처리였다. 다만 실제로 별개의 거래인데 입력값이 우연히 같은 경우까지 구별하려면 원천 거래 식별 정보가 필요하다. 현재 정의는 **제공된 컬럼이 동일한 행을 중복으로 처리한 기준**이다.

### 3.2 평균과 중앙값을 같이 본 이유

전세가는 고가 거래가 있는 분포다. 평균만 보면 일부 큰 값의 영향이 커질 수 있어, 계약 연월별 평균과 중앙값을 함께 그렸다.

이렇게 보면 전체 수준의 변화뿐 아니라, 평균과 중앙값의 간격도 볼 수 있다. 단, 월별 거래 구성 자체가 달라질 수 있으므로 이 그래프만으로 같은 아파트의 가격이 얼마나 변했는지 단정하지는 않았다.

이외에도 다음 관계를 확인했다.

- 면적에 따른 평균 전세가
- 층수에 따른 평균 전세가
- 계약 유형별 가격과 분포
- 건물 연식과 가격의 관계
- 면적·연식·층수·보증금의 분포와 극단값
- 변수 간 상관계수

히트맵에서는 면적과 보증금의 상관이 약 0.52, 건축 연도와 연식의 상관이 약 -0.99로 나타났다. 이는 당시 데이터의 관찰값이다. 입력 간 중복되는 정보와 가격에 직접 연결될 만한 변수를 검토하는 출발점으로 사용했다.

### 3.3 가격 사분위별로 지도를 그려 보기

보증금을 사분위로 나누어 위도·경도 산점도에 표시했다. 숫자 표에서는 잘 보이지 않던 가격대의 공간적 집중을 확인할 수 있었다.

```text
거래별 보증금
   → 가격 사분위로 구분
   → 좌표 위에 색으로 표시
   → 고가·저가 거래가 모이는 위치 확인
   → 입지 표현에 대한 가설 생성
```

여기서 좌표는 단순한 숫자 두 개가 아니라 주변 환경을 요약할 단서였다. 이후 최근접 거리, 반경 내 시설 수, 공원 면적, 공간 클러스터 등으로 표현을 확장했다.

### 3.4 금리는 그래프를 다시 그려 보며 해석했다

처음에는 금리별 보증금 중앙값을 비교했다. 그런데 같은 금리가 나타난 시기가 다르고 관측 빈도도 달라, 그 그래프만으로 관계를 판단하기 어렵다고 생각했다.

그래서 계약 연월에 금리를 연결하고, **월별 보증금 중앙값과 금리의 변화**를 함께 그렸다. 일부 반대 방향의 움직임이 보이더라도 다른 요인과 시차를 함께 고려해야 한다고 기록했다.

최종적으로 금리 관련 피처는 성능 개선이 크지 않아 채택하지 않았다. 이것은 해당 데이터와 피처·모델 조건에서의 결과다. ‘금리는 전세가에 영향을 주지 않는다’거나 ‘입지가 금리보다 중요하다는 인과관계를 증명했다’는 결론으로 확대하지 않는다.

### 3.5 계약 시점에 대한 추가 탐색

두 번째 EDA에서는 계절별 계약 수, 계약일 분포, 평일·주말 여부도 살폈다. 일반적으로 기대한 패턴이 데이터에서 그대로 나타나는지 확인하려는 시도였다.

도메인에서 들은 설명을 그대로 피처로 넣는 대신, 데이터에서 관찰하고 모델 성능으로 다시 확인하는 과정이 필요했다.

## 4. EDA를 피처로 연결하기

내가 맡은 주요 입지 피처는 ‘주변 시설이 좋다’는 말을 다음과 같이 나누는 방식이었다.

| 관점 | 질문 | 만든 특징 |
| --- | --- | --- |
| 접근성 | 가장 가까운 곳까지 얼마나 떨어져 있나? | 최근접 지하철·학교급별 거리 |
| 주변 선택지 | 일정 범위 안에 시설이 얼마나 있나? | 반경 내 학교급별 개수 |
| 녹지 규모 | 주변에 어느 정도 규모의 공원이 있나? | 반경 내 공원 면적 기반 밀도 |
| 지역적 유사성 | 가까운 거래들을 묶으면 도움이 되나? | K-Means·DBSCAN 클러스터 후보 |

### 4.1 지하철: 거리, 범주, 개수 중 무엇이 좋을까?

최근접 지하철 거리와 보증금을 산점도로 비교하고, 거리 구간별 보증금 중앙값도 확인했다. 이어 다음 표현을 실험했다.

1. 최근접 지하철까지의 연속형 거리
2. 일정 거리 안팎으로 나눈 범주형 표현
3. 특정 반경 내 지하철역 개수·밀도

팀 결과에서는 **최근접 거리만 사용하는 구성이 더 좋았다고 정리**했다. 최종 피처 목록에도 해당 거리가 남았다.

‘역세권’이라는 하나의 개념에도 여러 표현이 가능하고, 더 복잡하게 표현했다고 항상 더 좋은 것은 아니었다.

### 4.2 학교: 가까운 한 곳과 주변 개수는 다른 정보

학교 데이터에는 초등·중등·고등 구분이 있었다. 이를 하나로 합치지 않고 학교급별로 나누어 최근접 거리와 개수를 계산했다.

| 피처 | 설계 의도 |
| --- | --- |
| 최근접 초등·중·고교 거리 | 가장 가까운 시설에 대한 접근성 |
| 1km 이내 초등학교 수 | 가까운 생활권의 교육시설 분포 |
| 5km 이내 중학교 수 | 더 넓은 범위의 시설 분포 |
| 5km 이내 고등학교 수 | 더 넓은 범위의 시설 분포 |

1·5·5km는 개인 회고와 최종 전처리에서 확인되는 선택이다. 초등학교는 상대적으로 가까운 통학 환경을 고려한다는 가설에서 출발해 반경을 달리했다.

다만 이는 **학교의 거리와 수**다. 실제 배정 학군, 교육의 질, 학교 선호도를 직접 측정한 지표와는 구별해야 한다.

### 4.3 공원: 가까운 공원 하나에서 주변 녹지 규모로

초기 EDA에서는 최근접 공원 거리, 해당 공원의 면적, 500m·1km 안에 있는 경우의 가격 분포를 살폈다. 이후 주변 공원 전체의 면적을 집계하는 방향으로 확장했다.

개념적인 피처는 다음과 같다.

```text
공원 면적 기반 밀도
= 반경 r 안에 포함된 공원 면적의 합 / (π × r²)
```

같은 거리 안에 공원 하나가 있더라도 규모가 다르다는 점을 반영하려는 설계다. 최종 전처리 클래스에서는 공원 반경 기본값이 3km로 남아 있다.

이 값은 공원 좌표를 기준으로 전체 면적을 더하는 **면적 기반 대리 지표**다. 실제 원형 생활권과 공원 경계가 겹치는 면적을 공간 도형으로 계산한 값은 아니다. 분자·분모의 면적 단위도 맞추어야 한다.

## 5. 대규모 거리 계산을 어떻게 다뤘나?

거래는 약 180만 건이고 같은 아파트 위치가 반복해서 등장했다. 모든 거래와 모든 시설의 거리를 매번 계산하면 불필요한 연산이 커진다.

### 5.1 최근접 탐색과 거리 계산 역할 나누기

최근접 시설을 찾기 위해 `cKDTree`를 사용하고, 구면상의 거리 표현을 위해 Haversine 계산을 추가했다.

| 구성 | 목적 |
| --- | --- |
| 공간 인덱스 | 비교할 시설을 찾는 탐색 비용 줄이기 |
| Haversine | 위도·경도로부터 구면 거리 계산 |
| 배열 연산 | Python 반복문보다 묶어서 계산하기 |
| 고유 좌표 집계 | 같은 위치에 대한 반복 계산 줄이기 |
| 병렬 처리 | 독립적인 위치 계산 분산 |

`cKDTree`는 다차원 점의 최근접 이웃 검색에 사용하는 공간 인덱스다. 다만 원시 위도·경도에 대한 유클리드 최근접점이 항상 지표면 거리의 최근접점과 같지는 않다. [SciPy cKDTree 문서](https://docs.scipy.org/doc/scipy/reference/generated/scipy.spatial.cKDTree.html)

### 5.2 좌표를 한 번만 계산하고 원래 거래에 연결

공원·학교 집계에서는 고유 좌표에 대해 계산한 뒤 원래 데이터에 병합하는 방식을 사용했다.

```text
전체 거래
   → 고유한 아파트 좌표 추출
   → 좌표별 시설 거리·개수·면적 계산
   → 좌표 키로 원래 거래에 병합
```

이 방식은 연산량을 줄이는 것과 함께 **피처 생성 로직을 재사용 가능한 함수로 만드는 작업**으로 이어졌다. 새 데이터가 들어와도 같은 변환 흐름을 적용할 수 있게 하기 위해서다.

다만 실제 공개 구현을 다시 검토할 때는 좌표 순서, 도·라디안·km 단위, 거리 배열과 시설 배열의 인덱스 일치까지 확인해야 한다. 사용한 알고리즘 이름만으로 거리 피처가 정확하다고 보장되지는 않는다. 이는 후속 정비에서 우선 확인할 부분이다.

## 6. 만든 피처를 모두 남기지는 않았다

팀은 좌표 클러스터, 건물 연식 범주, 환승역 여부, 계절성, 금리 변화 등도 탐색했다.

| 채택된 주요 표현 | 제외한 후보의 예 |
| --- | --- |
| 면적·계약 연월·층수·건축 연도·좌표 | 계약일, 연식, 계약 유형 |
| 최근접 지하철 거리 | 거리 범주, 반경 내 지하철 수·밀도 |
| 학교급별 최근접 거리와 개수 | 일부 지역 클러스터 표현 |
| 공원 면적 기반 밀도 | 연식 범주, 계절 구분, 환승역 여부, 금리 변화 |

위는 팀의 최종 선택을 요약한 것이다. 나는 채택된 주요 입지 피처의 설계·구현을 맡아 팀의 모델링 실험에 연결했다.

클러스터 실험에서는 일부 평가에서 DBSCAN이 나았지만 결과가 안정적이지 않아 최종 반영하지 않았다. 건축 연도와 연식도 정보 중복을 고려해 비교한 뒤 하나를 남겼다.

피처를 만드는 것뿐 아니라, **남기지 않을 근거를 기록하는 일**도 중요했다. 성능 변화가 작은 후보와 결과가 불안정한 후보를 계속 유지하면 다음 실험을 해석하기 어려워진다.

## 7. 모델링: MAE를 기준으로 비교하기

전세보증금을 연속값으로 예측하는 회귀 문제이므로 주 지표는 MAE였다.

```text
MAE = 평균(|실제값 - 예측값|)
RMSE = sqrt(평균((실제값 - 예측값)²))
```

MAE는 원래 타깃과 같은 단위로 평균 오차를 보여 준다. RMSE는 큰 오차의 영향을 더 많이 받고, R²는 평균 예측 기준에 비해 얼마나 설명하는지를 보조적으로 살펴보는 지표다.

팀은 LightGBM을 중심으로 CatBoost, XGBoost, Random Forest 등을 비교했고 Optuna로 하이퍼파라미터를 탐색했다. 최종 공유 설정의 LightGBM에는 다음 값이 남아 있다.

| 항목 | 설정 예시 |
| --- | ---: |
| `num_leaves` | 1,200 |
| `learning_rate` | 0.035 |
| `n_estimators` | 2,000 |
| `feature_fraction` | 0.65 |
| 조기 종료 | 100회 |
| 교차검증 | 5-fold |

이는 해당 데이터에서 선택한 설정이다. 보편적인 최적값으로 제시하는 것은 아니다.

### 7.1 OOF 예측이 하는 일

5개 폴드 중 4개로 학습하고 남은 1개를 예측하는 과정을 반복했다. 각 행에는 그 행을 학습하지 않은 모델의 예측을 저장했다.

```text
Fold 1을 검증 → 해당 행들의 예측 저장
Fold 2를 검증 → 해당 행들의 예측 저장
...
Fold 5를 검증 → 해당 행들의 예측 저장
                  ↓
            전체 OOF 지표 계산
```

이를 통해 폴드별 지표와 전체 OOF MAE·RMSE·R²를 확인했다. 최종 코드에는 `KFold(shuffle=True)`가 사용되므로, 이 결과는 시간 순서나 미관측 아파트에 대한 일반화와는 따로 해석해야 한다.

## 8. 내가 시도한 앙상블: 폴드마다 다른 비중 주기

폴드 모델들을 단순 평균하는 것에 더해 **각 폴드의 검증 MAE를 이용하는 가중 평균**을 실험했다. 개인 Wrap-up에도 계산 방식과 그 한계를 기록했다.

### 8.1 MAE가 낮은 모델의 비중을 높이기

MAE는 낮을수록 좋으므로 역수를 이용해 비중을 만들고, 합이 1이 되도록 정규화했다.

```text
폴드 k의 검증 MAE: e_k
가중치: w_k = (1 / e_k) / Σ_j(1 / e_j)

최종 예측 = Σ_k w_k × prediction_k
```

실제 구현에서는 MAE가 0인 경우 등 수치적 예외도 처리해야 한다. 위 식은 당시 실험의 핵심 원리를 설명한 것이다.

이해를 위한 가상 예를 들면 다음과 같다.

| 모델 | 검증 MAE | 정규화 가중치 | 예측값 |
| --- | ---: | ---: | ---: |
| A | 1,000 | 2/3 | 30,000 |
| B | 2,000 | 1/3 | 40,000 |

단순 평균은 35,000이지만, 가중 평균은 약 33,333이다. 검증에서 더 나았던 A의 예측 쪽으로 이동한다. 이 숫자는 설명용이며 실제 실험 결과가 아니다.

### 8.2 가중 평균의 위험도 함께 기록했다

각 모델은 서로 다른 검증 폴드에서 평가된다. 낮은 MAE가 모델 자체의 우수함이 아니라 **그 폴드가 쉬웠기 때문**일 수도 있다.

또한 가중치 계산과 선택에 같은 검증 결과를 반복 사용하면 검증 조건에 맞춘 선택이 될 수 있다. 개인 회고에도 성능이 좋아 보였지만 위험한 방법이라고 남겼다.

따라서 ‘MAE 가중치로 예측 분산을 정량적으로 낮췄다’고까지 말하려면 반복 평가와 별도의 검증이 더 필요하다. 이번에 확인한 것은 해당 대회 조건에서 이 방식을 시도하고 비교한 경험이다.

### 8.3 여러 모델을 합치는 실험

폴드 내부 결합뿐 아니라 LightGBM·CatBoost·Random Forest를 결합하는 평균·가중 결합과 Stacking도 팀에서 실험했다. 하지만 다양한 조합이 LightGBM 단일 계열의 폴드 결합보다 항상 좋지는 않았다.

비슷한 오류를 내는 모델들을 합치면 보완 효과가 작을 수 있다. 다만 원인을 확정하려면 예측 오차 상관관계나 구간별 실패를 별도로 분석해야 한다.

현재 공개 `vote_soft()`는 이름과 달리 분류 확률을 결합하는 함수가 아니라 **회귀 예측값을 단순 평균**하는 함수다. MAE 가중 실험은 Wrap-up에 기록된 실험이고, 공개 최종 모듈의 평균 구현과 구분해야 한다.

## 9. 또 하나의 중심 기여: 노트북에서 공통 실행 구조로

이 프로젝트에서 모듈화는 마지막에 파일 이름을 정리한 작업으로 끝나지 않았다. 분석·학습·추론을 팀이 함께 사용할 수 있는 구조로 바꾸는 작업이었다.

앞선 비트코인 프로젝트에서는 각자 노트북을 발전시키면서 코드와 전처리 조건이 달라지는 경험을 했다. 이번에는 이런 차이를 줄이기 위해 공통 베이스라인, 실험 기록과 모듈 구조를 함께 고민했다.

### 9.1 문제를 이슈로 정의하고 단계적으로 바꾸기

내가 작성한 [Issue #38](https://github.com/boostcampaitech7/level2-competitiveds-recsys-08/issues/38)의 출발점은 대부분의 코드가 `baseline.ipynb`에서 실행되고 있다는 것이었다.

직접 작성한 초기 커밋에서는 전처리·학습·추론 관련 함수를 분리하고 실행 파일의 틀을 만들었다. 이후 입력·출력 형태, 전처리 클래스, 파일 구조, 모델 저장과 추론 코드를 차례로 정비했다.

최종 [PR #40](https://github.com/boostcampaitech7/level2-competitiveds-recsys-08/pull/40)에는 나와 팀원들의 변경이 함께 병합되었다. 내가 시작하고 반복해서 정리한 공통 구조 위에 모델 추가와 설정 관리가 함께 통합된 작업이다.

### 9.2 가장 큰 변화: 전처리를 한 곳으로 모으기

이전 코드에서는 `train.py`와 `test.py`가 각각 시설 파일을 읽고, 거리·밀도를 만들고, 피처를 선택했다. 같은 로직이 두 곳에 복사되어 있으면 한쪽만 고칠 위험이 있다.

나는 이를 `DataPreprocessor` 클래스로 모았다.

```text
이전
train.py: 로드 → 중복 제거 → 거리·밀도 → 피처 선택 → 학습
test.py:  로드 → 거리·밀도 → 피처 선택 → 예측

변경 후
                   DataPreprocessor
                 /                  \
       학습용 preprocess()      추론용 preprocess()
             ↓                      ↓
        X_train, y_train           X_test
```

학습 데이터에서만 중복을 제거하는 분기는 유지하면서, 시설 피처와 컬럼 선택은 공통 경로를 사용하게 했다. **전처리 방식을 바꿨을 때 학습과 추론에 함께 반영할 위치를 명확하게 만든 것**이다.

이 변경은 [전처리 클래스 도입 커밋](https://github.com/boostcampaitech7/level2-competitiveds-recsys-08/commit/1fd1cd874822e9acb4cb311a70957b831e9e2a42)의 diff에서 확인할 수 있다.

### 9.3 학습·추론·모델 저장의 책임 나누기

| 부분 | 공통 구조에서 맡는 일 |
| --- | --- |
| `src/data/features.py` | 위치·시설 피처 계산 |
| `src/data/preprocessor.py` | 로드, 전처리 순서, 피처 선택 |
| `src/models/` | 모델별 교차검증 학습 |
| `src/models/ensemble.py` | 여러 예측의 결합 |
| `src/utils.py` | 저장·불러오기, 설정 로드, 로깅 보조 |
| `configs/train_config.yaml` | 공통 조건과 모델 설정 |
| `train.py` | 선택한 모델의 학습과 저장 실행 |
| `test.py` | 모델 로드, 예측 결합, 제출 파일 생성 |

특히 모델 저장을 별도 함수로 빼고, 폴드별 파일을 다시 불러오는 공통 함수와 평균 결합 함수를 추가했다. 각자 작성한 학습 코드가 예측 결과 파일을 만드는 단계까지 연결되도록 하기 위한 작업이었다.

내가 정비한 공통 파이프라인에 팀원들이 추가한 설정·모델 구현도 함께 통합했다. **공통 구조의 틀을 만들고 전처리·저장·추론 연결을 정비한 일**이 내 역할의 중요한 부분이다.

### 9.4 모듈화에서 얻은 실질적인 효과

- 시설 피처를 바꿀 위치를 찾기 쉬워졌다.
- 학습·추론의 중복 전처리를 줄였다.
- 모델별 폴드 결과를 같은 저장 규칙으로 다룰 수 있게 했다.

작업 시간이 몇 % 줄었다는 측정은 없지만, 변경 지점과 재사용 경로는 코드로 확인할 수 있다. 내가 강조하고 싶은 성과도 이런 구체적인 구조 변화다.

## 10. 실험을 공유하는 방식도 코드와 연결하기

팀은 Notion에 실험 의도와 회의 내용을 남기고, GitHub의 Issue·Branch·PR로 변경을 관리했으며, W&B로 학습 지표를 공유했다.

개인 초기 모듈화 커밋에도 Holdout 학습, 폴드별 지표, OOF 결과와 특징 중요도를 W&B에 기록하는 함수가 포함되어 있다. 분석 결과와 학습 결과가 같은 실험 맥락에서 남도록 구성하려 했다.

| 기록 | 목적 |
| --- | --- |
| 실험 이슈·노트 | 무엇을 왜 바꾸는가? |
| 기능 브랜치·커밋 | 어느 코드 변경으로 실행했는가? |
| 설정·모델 저장 | 어떤 조건과 산출물인가? |
| 학습 로그·지표 | 결과가 어떻게 달라졌는가? |

현재 공개본에는 일부 W&B 코드가 비활성화되어 있다. 따라서 새로 저장소를 실행하면 모든 기록이 자동으로 연결되는 완성형 시스템이라고 볼 수는 없다. 이번 활동의 성과는 **공통 실행·기록 체계를 도입하고 정비한 것**이며, 환경까지 포함한 완전한 재현성 보장은 추가 확인이 필요하다.

## 11. 결과를 어떻게 해석했나?

랩업의 성능 그래프에서는 건축 연도와 외부 입지 피처 추가, Optuna 탐색 이후 MAE가 낮아지는 흐름이 제시된다. 단일 LightGBM의 후기 실험에서는 MAE가 약 3,500 수준으로 모이는 모습이 나타난다.

다만 그래프 중심의 자료이고 평가 조건이 모두 같다고 보장할 수 없으므로, 정확한 최종 MAE나 전체 개선율을 임의로 만들어 쓰지는 않는다.

확실하게 남긴 결과는 다음과 같다.

1. 주요 입지 피처를 모델 입력에 연결했다.
2. 성능이 좋지 않거나 불안정한 후보는 최종 목록에서 제외했다.
3. 폴드별 검증과 가중 결합을 비교했다.
4. 여러 모델의 결합이 항상 유리하지는 않았다.
5. 학습·추론·저장·기록을 공통 코드로 묶었다.
6. 팀 회고에는 최종 제출까지 리더보드 1위를 유지한 것으로 기록되어 있다.

가격 예측 개선과 협업 구조 개선은 다른 성과다. 모듈화 자체가 MAE를 얼마나 낮췄다고 계산할 수는 없지만, 팀의 실험을 공유·확장할 수 있는 기반을 만들었다는 의미가 있다.

## 12. 다음에 보완하고 싶은 것

### 12.1 무엇에 일반화할지에 맞춰 검증하기

같은 아파트의 여러 거래가 서로 다른 폴드에 들어갈 수 있다. 이런 무작위 검증과 처음 보는 단지·미래 시점에 대한 예측은 난도가 다를 수 있다.

| 검증 | 확인하려는 것 |
| --- | --- |
| 시간 순서 분리 | 이후 계약 시점에도 맞는가? |
| 단지·좌표 그룹 분리 | 미관측 위치에도 적용되는가? |
| 지역별 성능 | 특정 지역에만 좋은가? |
| 가격대·면적대별 오차 | 일부 고가·대형 거래에서 실패하는가? |

OOF를 사용했다는 사실만으로 모든 형태의 누수가 사라지는 것은 아니다. 전처리 학습 범위와 모델·가중치 선택 과정까지 함께 점검해야 한다.

### 12.2 지리 계산을 작은 검증 예제로 확인하기

동일 좌표의 거리 0, 이미 거리를 아는 두 점, 특정 반경 안팎의 시설, 학교급별 개수 같은 작은 예제로 피처 계산을 확인하고 싶다.

지표면 거리에 맞는 탐색 방법, 좌표 순서, 시설의 개설 시점, 공원 면적 단위도 함께 검증해야 한다. 이동 거리와 직선 거리, 실제 통학 가능성과 단순 접근성도 다른 개념이다.

### 12.3 공통 구조를 재현 가능한 실행으로 완성하기

다음에는 코드·설정뿐 아니라 데이터 버전, 의존성, 생성 피처, 폴드 분할, 모델 파일과 로그 ID를 하나의 실험 단위로 묶고 싶다.

모듈화는 그 출발점이었다. 이후에는 전처리 결과를 검사하는 테스트와 실행 점검, 설정·모델의 호환성 관리까지 연결할 수 있다.

## 13. 나의 기여를 한 번에 정리하면

| 축 | 실제로 한 일 |
| --- | --- |
| EDA | 품질·분포·시간·공간 분석, 금리와 거래 데이터 연결, 시설별 관계 시각화 |
| 피처 엔지니어링 | 지하철·학교 거리, 학교급별 반경 집계, 공원 면적 기반 피처 설계·구현 |
| 계산 구조 | KDTree 계열 탐색, 배열 연산, 고유 좌표 재사용과 병렬 계산 |
| 앙상블 | MAE 역수 기반 폴드 가중치 실험, 평균·모델 결합 비교 |
| 모듈화 | 초기 함수·파일 구조, 공통 전처리 클래스, 중복 제거, 모델 저장·로드와 평균 추론 함수 |
| 협업 | 개인 코드의 공통 파이프라인 통합, Issue·PR·문서 및 실험 기록 활용 |

내 역할은 분석한 내용을 설명하는 데서 끝나지 않았다. **관찰을 피처로 만들고, 피처를 팀의 학습·추론 코드에 넣고, 다른 실험에서도 사용할 수 있는 구조로 정리하는 일**까지 이어졌다.

## 14. 질문으로 되짚어 보기

### EDA에서 모델링으로 연결한 대표 사례는?

지하철 거리와 가격을 여러 구간으로 살펴본 뒤 연속 거리·범주·반경 내 개수 표현을 비교한 것이다. 학교도 최근접 거리에서 학교급별 반경 집계로 확장했다.

### 모듈화에서 가장 중요한 변경은?

학습과 추론 파일에 복사되어 있던 전처리를 `DataPreprocessor`로 모은 것이다. 두 경로의 피처 생성과 선택을 함께 관리할 수 있게 했다.

### 가중 앙상블을 왜 시도했나?

모든 폴드의 예측을 같은 비중으로 합치는 대신 검증 오차를 반영해 보고 싶었다. 동시에 폴드 난도 차이와 검증 과적합 위험도 확인했다.

### 입지가 금리보다 중요하다는 것을 증명했나?

이번 데이터에서 입지 피처가 최종 모델에 채택되고 금리 피처의 효과가 작았다는 관찰은 있다. 하지만 이를 일반적인 시장 인과관계로 해석하지 않는다.

### 이 프로젝트에서 가장 크게 얻은 것은?

EDA, 피처 설계, 모델 실험, 공통 코드 정리를 하나의 흐름으로 연결한 경험이다. 좋은 아이디어를 팀이 다시 실행하고 비교할 수 있게 만드는 일까지 내 역할로 가져갔다.
