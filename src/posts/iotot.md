## 1. 무엇을 연구했나?

보안 취약점을 관리하려면 먼저 네트워크에 **어떤 장치가 있는지** 알아야 한다. 그런데 공장, 발전소, 수처리 시설, 건물 자동화 시스템에서는 장치를 알아내기 위해 보내는 탐색 패킷조차 운영에 부담을 줄 수 있다.

이 연구에서는 운영 기술, 즉 **OT(Operational Technology) 환경에서 장치를 어떻게 식별할지**를 조사했다. 특히 장치에 추가 요청을 보내는 대신 이미 발생하는 트래픽을 관찰하는 수동적 스캐닝과, 그 트래픽을 머신러닝 입력으로 바꾸는 특징에 주목했다.

> 핵심 질문은 ‘기존 IoT 장치 식별에서 유용했던 트래픽 특징과 학습 방법을 OT에도 적용할 수 있을까?’였다.

| 항목 | 연구 내용 |
| --- | --- |
| 논문 | 운영 기술 환경에서 수동적 스캐닝 기반 장치 식별의 비교 분석 |
| 게재 | 한국소프트웨어감정평가학회 논문지, 19권 3호, 105–118쪽, 2023년 |
| 연구 형태 | 기존 연구와 도구의 비교 분석, 특징 정보 분류, 후속 연구 방향 제시 |
| 주요 분석 대상 | IT·OT 스캐닝, IoT 머신러닝 장치 식별 연구 18건, OT 장치 식별 연구 |
| 특징 분류 | 프로토콜 기반 / 패킷 속성 기반 / 통신 행위 기반 |
| 나의 참여 중심 | 관련 자료조사와 머신러닝 관점의 특징·모델 분석 |

이 글에서는 논문의 조사 결과를 먼저 정리하고, 이를 바탕으로 실제 머신러닝 실험을 설계할 때 생각해야 할 내용을 덧붙였다. 뒤에서 제시하는 데이터 파이프라인과 실험 설계는 이해와 확장을 위한 정리이며, 이 논문에서 새로 구현해 성능을 검증한 시스템을 뜻하지 않는다.

## 2. OT에서 장치 식별이 중요한 이유

### 2.1 OT와 ICS는 무엇인가?

OT는 물리적 설비와 공정을 감시하거나 제어하는 기술을 말한다. ICS(Industrial Control System)는 산업 제어 시스템으로, OT를 설명할 때 자주 등장하는 대표적인 시스템이다.

| 장치·시스템 | 역할을 이해하기 위한 예시 |
| --- | --- |
| PLC | 센서 입력과 제어 로직에 따라 모터·밸브 등을 제어 |
| HMI | 운영자가 설비 상태를 보고 명령을 입력하는 인터페이스 |
| RTU | 원격 현장의 상태를 수집하고 제어 명령을 전달 |
| SCADA | 여러 현장의 설비를 감시하고 제어하는 시스템 |
| 건물 자동화 시스템 | 냉난방·조명·화재 경보 등 건물 설비 관리 |

어떤 장치가 있는지 모르면 제조사·모델·소프트웨어와 관련된 취약점을 연결하기 어렵다. 따라서 자산 식별은 보안 관리의 출발점이다.

```text
장치 존재 확인
   → 제조사·모델·역할 등 식별
   → 관련 취약점·구성 확인
   → 운영 조건에 맞는 보호 조치 검토
```

단, 장치 종류를 분류했다고 곧바로 정확한 펌웨어 버전이나 모든 취약점까지 알아낸 것은 아니다. **식별 결과의 세밀함**을 구분해야 한다.

### 2.2 일반 IT의 방법을 그대로 적용하기 어려운 이유

OT에서는 장시간 연속 운영, 실시간 제어, 제한된 장치 자원, 오래된 설비와 여러 제조사의 공존을 고려해야 한다. 통신 지연이나 장치 장애가 물리적인 공정에 영향을 줄 수도 있다.

논문은 이러한 가용성 요구를 중심으로 기존 스캐닝 방법의 적용 한계를 분석했다. 이는 OT에서 기밀성과 무결성이 중요하지 않다는 뜻이 아니라, **장치 식별 과정 자체가 운영을 방해하는지도 함께 평가해야 한다**는 의미다.

## 3. 능동적 스캐닝과 수동적 스캐닝

### 3.1 능동적 스캐닝: 직접 물어보기

대상 장치에 탐색 요청을 보내고 응답을 분석한다. Nmap의 운영체제 추정처럼 응답 헤더와 알려진 특징을 비교하는 방법이 여기에 해당한다.

```text
스캐너 → 탐색 요청 → OT 장치
스캐너 ← 응답 패킷 ← OT 장치
                 ↓
          장치·운영체제 정보 추정
```

필요한 응답을 유도할 수 있지만, 그 요청을 장치가 처리해야 한다. 논문이 조사한 선행연구에서는 통신 지연, 오류, 장치 오작동 등 가용성에 영향을 준 사례가 보고되어 있다.

이 사례들은 해당 조건에서 관찰한 결과다. 모든 능동 스캔이 반드시 장애를 만든다는 뜻으로 일반화하지 않고, 대상과 탐색 강도에 따라 적용 조건을 평가해야 한다.

### 3.2 수동적 스캐닝: 이미 오가는 통신 관찰하기

장치에 별도의 식별 요청을 보내지 않고 기존 트래픽을 관찰한다. p0f의 운영체제 추정이 대표적인 예다.

```text
OT 장치 A ← 기존 운영 트래픽 → OT 장치 B
                       │
                       └─ 관찰 가능한 지점에서 복사·수집
                                      ↓
                              특징 추출 및 장치 식별
```

장치에 추가 탐색 요청을 보내는 부담을 줄인다는 장점이 있다. 그러나 관찰 가능한 트래픽이 있어야 하며, 수집 위치와 장치의 동작 상태에 따라 식별 범위가 달라진다.

| 비교 기준 | 능동적 스캐닝 | 수동적 스캐닝 |
| --- | --- | --- |
| 정보 확보 | 요청을 보내 응답 유도 | 기존 트래픽 관찰 |
| 장치에 가하는 탐색 부하 | 발생 | 별도 탐색 요청은 없음 |
| 조용한 장치 | 응답을 유도할 수 있음 | 관찰 기간에 통신이 없으면 어려움 |
| 식별에 필요한 정보 | 응답에 포함될 수 있음 | 기존 트래픽에 있어야 함 |
| 주요 검토 조건 | 가용성 영향과 허용 가능한 탐색 범위 | 관측 지점, 수집 시간, 트래픽 가시성 |

### 3.3 수동적이라고 모든 장치를 볼 수 있는 것은 아니다

스위치 네트워크의 한 지점에서 다른 모든 장치 간 유니캐스트 통신을 자동으로 볼 수 있는 것은 아니다. 포트 미러링 등 필요한 관측 조건이 마련되어야 한다.

논문이 인용한 연구에서는 미러링이 지원되지 않는 환경에서 브로드캐스트를 발생시킨 HMI는 식별했지만, 해당 패킷을 발생시키지 않은 PLC는 식별하지 못했다.

장치의 동작 특성도 문제다.

- **이벤트 기반 장치:** 화재 경보처럼 특정 상황에서만 유의미한 통신을 할 수 있다.
- **긴 세션:** 이미 연결된 세션이 오래 유지되면 초기 연결 패킷을 관찰하기 어렵다.
- **드문 통신:** 짧은 관측 시간에는 특징을 계산할 만큼 패킷이 없을 수 있다.

따라서 관측되지 않았다는 사실을 장치가 존재하지 않는다는 뜻으로 해석하면 안 된다.

## 4. 규칙 기반에서 머신러닝으로 넘어가려면

장치별 통신 규칙을 사람이 작성하는 방식은 규칙의 근거를 이해하기 쉽지만, 새로운 유형이나 버전이 늘어날 때 규칙을 계속 관리해야 한다.

머신러닝은 여러 트래픽 특징과 라벨을 바탕으로 구분 기준을 학습한다. 그러나 이를 ‘새 장치가 와도 아무 작업 없이 자동으로 알아내는 방식’으로 설명하면 과장이다.

| 방식 | 분류 기준을 만드는 방법 | 새 유형이 생겼을 때 남는 일 |
| --- | --- | --- |
| 규칙 기반 | 사람이 조건·서명을 작성 | 규칙 추가 및 검증 |
| 지도학습 기반 | 라벨 데이터로 모델 학습 | 데이터 확보, 라벨 정의, 모델 갱신 및 검증 |

**규칙 관리 비용 일부를 데이터와 모델 관리로 옮기는 것**에 가깝다. 실제 장점은 동일 조건에서 관리 비용과 식별 성능을 비교해야 확인할 수 있다.

또한 분류 목표를 먼저 정해야 한다.

| 목표 | 예시 | 필요한 검증 |
| --- | --- | --- |
| 장치 역할 | PLC / HMI / 센서 | 역할별 구분 능력 |
| 제조사·모델 | 특정 제조사의 특정 제품군 | 유사 모델 간 혼동 |
| 개별 장치 | 같은 모델의 장치 A와 B | 물리적 개체 구분 능력 |
| 미지 유형 감지 | 학습에 없던 장치를 미지로 처리 | 거절·미탐 성능 |

이 네 가지는 서로 다른 과제다. 하나의 높은 정확도가 나머지 능력까지 보장하지는 않는다.

## 5. IoT Sentinel에서 참고한 관점

IoT Sentinel은 네트워크에 새로 연결된 IoT 장치의 통신을 이용해 장치 유형을 식별하고 보안 정책 적용으로 연결하는 연구다. 초기 설정 단계의 통신에서 패킷당 23개 특징을 추출하고, 중복 특징 벡터를 제거한 뒤 앞선 12개를 연결해 276차원 입력을 구성한다. 장치 유형별 Random Forest와 후보 구분 절차를 사용한다. [IoT Sentinel 원문, Section IV](https://arxiv.org/html/1611.04880)

내가 이 연구에서 주목한 것은 **패킷을 어떤 표현으로 바꾸면 장치 특성을 학습할 수 있는가**였다. 다만 OT에 그대로 옮기려면 초기 설정 트래픽을 실제로 확보할 수 있는지부터 확인해야 한다. 오래 동작하는 OT 장치를 운영 도중 관찰한다면 같은 입력 조건이 주어지지 않을 수 있기 때문이다.

첨부 논문은 IoT Sentinel만 복제한 연구가 아니라, 이를 포함한 IoT 식별 연구들을 비교하고 특징을 분류한 조사다. OT에서도 해당 설계가 동일하게 작동한다는 실험 결과를 제시한 것은 아니다.

## 6. 머신러닝의 입력: 특징을 세 가지로 나누기

이 논문에서 중심적으로 정리한 내용은 트래픽 특징의 분류다.

```text
네트워크 트래픽 특징
  ├─ 프로토콜 기반: 무엇으로 통신하는가?
  ├─ 패킷 속성 기반: 어떤 형태의 패킷인가?
  └─ 통신 행위 기반: 언제, 얼마나, 어떤 흐름으로 통신하는가?
```

서로 완전히 독립적인 범주는 아니다. 실제 모델에서는 여러 범주의 특징을 함께 사용할 수 있다.

### 6.1 프로토콜 기반 특징

프로토콜의 사용 여부나 비중을 특징으로 삼는다. 예를 들어 ARP, IP, TCP, UDP, DNS, DHCP 등의 통신 패턴을 관찰할 수 있다.

| 확인할 정보 | 구분에 도움을 줄 수 있는 이유 | 주의점 |
| --- | --- | --- |
| 특정 프로토콜 사용 여부 | 장치의 서비스·구현 방식 반영 | 여러 장치가 같은 프로토콜 사용 가능 |
| 프로토콜별 패킷 비중 | 장치 역할과 통신 상대의 차이 반영 | 관측 시간·운영 상태 영향 |
| 산업용 프로토콜 관련 정보 | OT 장치·서비스 특성 반영 | 해당 프로토콜을 쓰지 않는 장치에는 적용 어려움 |

논문에서는 IoT의 일반 IT 프로토콜과 OT의 Modbus, Profinet, OPC UA, DNP3, BACnet 등 사용 맥락의 차이를 살폈다. 이는 OT가 일반 IP 통신을 사용하지 않는다는 뜻은 아니다.

프로토콜 계층도 구분해서 이해해야 한다. 예를 들어 EAPoL은 이름에 인증 기능이 드러나더라도 IP 위의 일반 네트워크 계층 프로토콜로 분류하지 않는다. 특징 목록과 정확한 계층 분류는 별도로 점검할 필요가 있다.

### 6.2 패킷 속성 기반 특징

| 특징 | 의미 | 모델이 활용할 수 있는 정보 | 한계 |
| --- | --- | --- | --- |
| IPv4 TTL | 패킷의 생존 범위를 제한하는 헤더 값 | 송신 스택의 설정과 경로 특성 | 라우팅 경로에 따라 관측값 변화 |
| TCP Window | 수신 측이 알리는 수신 가능 범위 | TCP 스택·버퍼·통신 상태의 차이 | 장치 고유값이라고 보장되지 않음 |
| 패킷 길이 | 정의한 계층에서의 패킷 크기 | 메시지 형태와 트래픽 특성 | 헤더 포함 범위·오프로딩·수집 조건 영향 |
| 페이로드 정보 | 데이터 내용이나 통계 | 메시지 형식의 차이 | 암호화·개인정보·프로토콜 의존성 |
| 페이로드 엔트로피 | 바이트 분포의 불확실성을 나타내는 통계 | 데이터 성격의 차이에 대한 단서 | 높은 값만으로 암호화 여부 확정 불가 |

**TTL**은 장치의 통신 주기와 다른 특징이다. 송신 시 설정되며 경로에서 감소하므로, 같은 장치도 다른 지점에서 관측하면 값이 달라질 수 있다. [IPv4 명세 RFC 791, Section 3.1](https://www.rfc-editor.org/rfc/rfc791.html)

**TCP Window**는 ‘응답하기 전까지 처리 가능한 데이터 양’이라고만 외우기보다, 수신 측이 송신 측에 알리는 수신 윈도우로 이해하는 편이 정확하다. 원시 필드와 윈도우 스케일 적용값도 구분해야 한다. [TCP 명세 RFC 9293](https://www.rfc-editor.org/rfc/rfc9293.html)

페이로드 엔트로피는 압축·암호화 데이터에서 높게 나타날 수 있지만, 표본 길이와 데이터 구성에도 영향을 받는다. ‘평문은 항상 낮고 암호문은 항상 높다’는 식으로 결정적인 식별 규칙으로 사용하지 않는다.

### 6.3 통신 행위 기반 특징

개별 패킷 하나보다 여러 패킷의 관계를 요약한다.

| 특징 | 의미 | 계산 단위를 먼저 정할 것 |
| --- | --- | --- |
| IAT | 연속된 패킷의 관측 시각 차이 | 장치 전체 / 방향별 / 흐름별 중 무엇인가? |
| Packet Count | 구간 안의 패킷 수 | 관측 구간의 길이는 얼마인가? |
| Flow Volume | 흐름 또는 구간의 전송량 | 바이트 기준과 방향은 무엇인가? |
| Flow Duration | 흐름의 지속 시간 | 흐름 종료·타임아웃을 어떻게 정했는가? |
| 주기성 관련 통계 | 반복 전송 간격과 그 변동 | 같은 종류의 메시지를 묶었는가? |

IAT는 다음과 같이 계산한다.

```text
패킷 도착 시각: 0.00, 1.00, 2.02, 3.01초
IAT:              1.00, 1.02, 0.99초
```

이 예제는 거의 1초마다 패킷이 관찰되는 상황을 설명하기 위한 가상 데이터다. 논문 실측값이 아니다.

여기서 **IAT와 실제 제어 주기는 같지 않을 수 있다.** 요청과 응답을 한꺼번에 섞거나, 여러 상대와의 패킷을 합치거나, 재전송·패킷 손실이 생기면 관측 간격이 달라진다. 네트워크 지연과 타임스탬프 정밀도도 영향을 준다.

## 7. OT에 맞는 특징을 고민한다는 것

### 7.1 통신 주기성은 유력한 후보이지 정답은 아니다

센서 상태 보고나 제어 요청에는 반복되는 패턴이 있을 수 있다. 따라서 IAT의 평균·분산, 일정 간격의 반복 여부는 검토할 가치가 있다.

하지만 모든 OT 장치가 일정 주기로 통신하지는 않는다. 같은 장치도 생산 상태, 경보 발생, 유지보수 여부에 따라 패턴이 바뀔 수 있다.

```text
장치 특성
  + 현재 공정 상태
  + 통신 상대의 요청 주기
  + 네트워크·관측 조건
  = 관찰된 트래픽 패턴
```

이 중 무엇을 모델이 배웠는지 구별해야 한다. 장치 종류 대신 특정 공장의 폴링 설정을 외웠다면 다른 현장에서 성능이 떨어질 수 있다.

### 7.2 방향과 포트는 기준을 명확히 해야 한다

‘송신·수신’은 어떤 장치를 기준으로 하는지 정해야 한다. 포트 번호 역시 서비스 포트와 임시 포트가 섞일 수 있고, 동일한 포트를 여러 장치가 사용할 수 있다.

방향별 통계와 포트 사용 패턴은 후속 특징 후보로 검토할 수 있다. 다만 이 논문이 이를 포함한 최종 OT 전용 특징 세트를 학습하고 효과를 검증했다고 표현하지는 않는다.

### 7.3 특징에 가중치를 주었다는 표현도 구체적이어야 한다

‘통신 주기 피처의 가중치를 강화했다’는 말은 실제 구현 방법이 있어야 성립한다. 후보로 중요하게 검토했다는 것과 학습 과정에서 특정 가중치를 부여했다는 것은 다르다.

특히 Decision Tree나 Random Forest에서는 한 수치 특징에 양의 상수를 곱하는 것만으로 그 특징을 더 중요하게 학습하도록 만들 수 있다고 보기 어렵다. 값의 순서가 그대로라면 같은 분할이 가능하기 때문이다.

실제 효과는 특징 집합을 바꾼 실험, 특징 제거 실험, 검증 데이터에서의 중요도 분석 등을 통해 확인해야 한다.

## 8. 조사에서 확인한 결과

### 8.1 IoT에서는 다양한 모델과 특징이 연구되었다

논문 Table 2는 2017–2022년의 IoT 식별 연구 18건을 정리했다. Random Forest, Decision Tree, KNN, SVM, Naive Bayes, Gradient Boosting과 여러 시계열·신경망 계열 방법이 등장한다.

아래는 논문이 인용해 정리한 일부 결과다. **우리 연구가 직접 측정한 모델 성능이 아니다.**

| 선행연구 | 사용 방법의 예 | 첨부 논문에서 소개한 결과 |
| --- | --- | --- |
| IoT Sentinel [27] | Random Forest | 27개 장치 중 17개는 약 95% 이상, 나머지 10개는 약 50% 정확도 |
| 주기 통신 기반 AuDI [35] | KNN, 주기성 관련 특징 | 33개 장치에서 98.2% 정확도 |
| 흐름 기반 연구 [34] | LDA, KNN, CART 등 | 27개 장치에서 평균 90.3% 정확도, 91% F1 |
| IoTDevID [44] | RF, DT, GB | 두 데이터셋에서 각각 93.3%, 94.3% 정확도 |

데이터셋, 장치 수, 분류 목표, 분할 방법이 다르므로 이 숫자만으로 모델 순위를 매기면 안 된다. 일부 연구의 높은 최대 정확도와 전체 평균도 구분해야 한다.

### 8.2 OT에서는 관측 조건과 적용 제약이 크게 작용했다

| 조사한 접근 | 확인한 가치 | 함께 나타난 한계 |
| --- | --- | --- |
| 산업 프로토콜 정보 이용 | 제조사·모델 관련 정보 확보 | 특정 프로토콜에 의존 |
| 수동적 도구 사용 | 추가 탐색 없이 일부 자산 정보 확인 | 관측 위치·브로드캐스트 여부 등에 영향 |
| TTL·IP ID·MAC 관련 정보 | 패킷에서 식별 단서 추출 | 서로 다른 장치의 특징값이 겹칠 수 있음 |
| CLRT 기반 접근 | 응답 시간 특성을 장치 구분에 활용 | TCP와 ACK 관련 조건 필요 |

논문이 소개한 OT 연구에는 약 5개월 또는 11일 동안 트래픽을 수집한 사례가 있다. 이는 기존 연구의 관측 기간이며, 이번 연구에서 직접 그 기간 동안 수집했다는 뜻은 아니다.

CLRT(Cross-Layer Response Times)는 요청·응답 시간과 전송 계층 ACK 시간의 차이를 활용하는 접근이다. 단순히 연속 패킷 사이 간격을 재는 IAT와 구별해야 한다. 조사된 연구에는 TCP 사용과 quick ACK 설정 등의 적용 조건도 있었다.

### 8.3 ‘OT 연구가 부족하다’는 결론의 범위

조사한 범위에서는 OT에 특화된 특징 연구와 다양한 머신러닝 적용이 IoT보다 부족했다. 이는 **2023년 논문이 검토한 문헌 집합에 대한 결론**이다. 현재까지 전 세계에 관련 연구가 없다는 뜻은 아니다.

따라서 다음 단계는 IoT에서 유용했던 특징을 그대로 받아들이는 것이 아니라, OT 데이터에서 적용 가능성과 식별력을 확인하는 것이다.

## 9. 머신러닝 실험으로 확장한다면

이 절은 논문의 연구 방향을 구체화한 실험 설계 노트다. 수행 완료한 실험 결과와 구분한다.

### 9.1 파이프라인

```text
관측 지점·대상·운영 상태 정의
    ↓
패킷 캡처 데이터(.pcap)와 장치 목록 확보
    ↓
패킷 파싱 및 장치·흐름·방향 구분
    ↓
정해진 시간창 또는 패킷 수로 집계
    ↓
프로토콜 / 속성 / 행위 특징 계산
    ↓
정답 라벨과 연결하고 데이터 분리
    ↓
모델 학습 및 별도 데이터 평가
    ↓
성능·시간·커버리지·실패 사례 분석
```

Wireshark·TShark는 패킷을 관찰·확인하는 데, Python·Pandas·NumPy는 정형화와 통계 계산에, Scikit-learn은 모델 비교에 사용할 수 있다. 이는 구현 시 사용할 수 있는 도구 예시이며, 이 논문의 실험 코드와 실행 환경을 재현했다는 뜻은 아니다.

### 9.2 학습 표본 한 개를 먼저 정의하기

모델의 입력 한 행을 ‘장치 한 대의 10초 구간’으로 만들지, ‘하나의 흐름’으로 만들지에 따라 과제가 달라진다. 아래는 **예시 스키마**다.

| 열 | 용도 |
| --- | --- |
| device_instance_id | 데이터 분리·추적용 개별 장치 ID |
| capture_session_id | 수집 세션 분리용 ID |
| window_start | 관측 구간 식별용 시각 |
| packet_count, byte_count | 구간 내 통신량 |
| iat_mean, iat_std | 정의한 방향·흐름에서의 간격 통계 |
| length_mean, length_std | 동일 기준으로 계산한 패킷 크기 통계 |
| ttl_mode | 관측 TTL의 대표값 |
| tx_rx_ratio | 대상 장치 기준 방향별 비중 |
| protocol_ratios | 프로토콜별 사용 비중 |
| label | 장치 종류 또는 제조사·모델 등의 정답 |

분리용 ID가 모두 학습 입력이 되는 것은 아니다. 특히 개별 IP·MAC 주소를 그대로 넣으면 장치 특성이 아니라 해당 실험실의 주소 배치를 외울 수 있다.

### 9.3 OT 특징의 효과는 단계적으로 비교하기

| 실험 | 특징 집합 | 확인하려는 질문 |
| --- | --- | --- |
| A | 프로토콜 특징 | 사용하는 통신 종류만으로 구분 가능한가? |
| B | A + 패킷 속성 | 헤더·길이 정보가 추가로 도움이 되는가? |
| C | B + 행위 특징 | 주기·통신량이 실제 일반화 성능을 높이는가? |
| D | C에서 특정 특징 제거 | 주기 관련 특징을 빼면 무엇이 달라지는가? |

모델은 Decision Tree 같은 해석하기 쉬운 기준 모델과 Random Forest 등을 비교할 수 있다. 모델을 많이 돌리는 것보다 동일한 데이터 분할·전처리 조건을 지키고 오류 원인을 확인하는 일이 먼저다.

트리 깊이, 최소 리프 표본 수, 트리 개수 등의 조정값은 검증 데이터로 선택해야 한다. 테스트 결과를 반복해서 보며 값을 고르면 성능 추정이 낙관적으로 바뀔 수 있다.

## 10. 검증에서 가장 중요한 구분

### 10.1 ‘학습하지 않은 신규 장치’는 두 가지다

| 상황 | 의미 | 적절한 평가 |
| --- | --- | --- |
| 알려진 종류의 새 장치 | 같은 모델의 다른 물리적 개체 | 장치 개체 단위로 학습·테스트 분리 |
| 처음 보는 종류의 장치 | 정답 클래스 자체가 학습에 없음 | 미지 장치 거절·탐지 평가 |

일반적인 다중 클래스 분류기는 입력을 기존 클래스 중 하나로 분류한다. 따라서 학습에 없는 종류를 자동으로 알아내는 능력은 별도로 설계해야 한다.

### 10.2 패킷 행을 무작위로 나누면 위험할 수 있다

같은 장치·같은 수집 세션의 인접 구간은 매우 비슷하다. 이를 무작위로 나누면 사실상 같은 패턴이 학습과 테스트에 동시에 들어갈 수 있다.

| 분리 방식 | 확인할 수 있는 것 |
| --- | --- |
| 수집 세션별 분리 | 다른 수집 시점에서도 식별되는가? |
| 장치 개체별 분리 | 같은 제품의 새 장치에도 적용되는가? |
| 시간 순서 분리 | 이후 운영 상태·버전 변화에 견디는가? |
| 현장·네트워크별 분리 | 다른 주소·토폴로지·공정에도 적용되는가? |
| 장치 유형을 통째로 제외 | 미지 유형으로 처리할 수 있는가? |

서로 겹치는 시간창도 양쪽으로 나뉘지 않게 관리해야 한다. 특징 선택과 전처리 기준 역시 학습·검증 데이터에서 정하고 테스트에는 적용만 한다.

### 10.3 정확도 외에 무엇을 볼까?

- **장치별 Precision·Recall·F1:** 특정 장치만 잘 맞는지 확인
- **Macro-F1:** 장치별 성능을 동일 비중으로 요약
- **혼동행렬:** 어떤 장치끼리 혼동되는지 확인
- **식별 소요 시간:** 최초 관측 후 언제 판단할 수 있는지 확인
- **커버리지:** 실제 대상 중 관측·판단한 장치가 얼마나 되는지 확인
- **미지 장치의 오수용:** 처음 보는 장치를 기존 종류로 잘못 확정하는 비율 확인
- **비용:** 특징 추출 시간, 예측 시간, 저장량과 운영 부담 확인

커버리지도 분모가 필요하다. 전체 자산 목록을 알고 있다면 그중 식별한 비율을 계산할 수 있지만, 목록 자체가 없다면 관측하지 못한 장치까지 정확히 셀 수는 없다.

## 11. 이 연구에서 나의 기여

나는 관련 자료조사와 머신러닝 쪽에 비중을 두고 참여했다. 중심적으로 정리한 것은 **기존 연구가 어떤 데이터·특징·모델로 장치를 구분했으며, 그 접근을 OT에 옮길 때 무엇을 검토해야 하는가**였다.

| 참여 영역 | 정리한 내용 |
| --- | --- |
| 선행연구 조사 | IoT·OT 장치 식별, 능동·수동 스캐닝의 접근과 제약 비교 |
| 머신러닝 관점 분석 | 연구별 입력 특징, 사용 모델, 데이터셋, 평가 지표 검토 |
| 특징 이해와 분류 | 프로토콜·패킷 속성·통신 행위 관점에서 특징의 의미 정리 |
| OT 적용 가능성 검토 | 주기성, 긴 세션, 드문 통신, 가용성 요구와 특징의 관계 검토 |
| 후속 연구 방향 | 특징과 알고리즘 조합, 관측 시간, 식별 범위 등의 검증 과제 정리 |

내가 배운 점은 분류 모델을 선택하기 전에 **표본 하나의 의미, 라벨의 수준, 관측 조건과 검증 방법**을 먼저 정의해야 한다는 것이다. 데이터가 어떤 환경을 반영하는지 모르면 높은 정확도도 설명하기 어렵다.

## 12. 논문이 제시한 다음 연구 과제

논문 Section 5의 방향은 네 가지로 정리된다.

| 과제 | 핵심 질문 |
| --- | --- |
| 특징과 알고리즘의 조합 | OT에서 어떤 특징과 모델이 실제로 유효한가? |
| 적정 관측 시간 | 얼마나 기다려야 필요한 장치를 충분히 식별할 수 있는가? |
| 제한적인 능동 스캐닝 | 가용성 영향을 평가한 뒤 어느 범위까지 적용할 수 있는가? |
| 식별 커버리지와 대안 | 두 방법으로도 식별하지 못하는 장치는 어떻게 다룰 것인가? |

따라서 ‘수동 방식만이 항상 정답’이라는 결론은 아니다. 수동 관측의 장점을 살리되, 관측 불가능한 장치와 허용 가능한 탐색 범위를 함께 검토하는 것이 과제다.

장치 유형을 추정하는 모델뿐 아니라 **판단할 정보가 부족하다는 사실을 드러내는 시스템**도 필요하다. 미관측, 저신뢰, 미지 유형을 구별할 수 있어야 사람이 결과를 해석하기 쉽다.

## 13. 짧게 설명할 때 기억할 답변

### 연구를 한 문장으로 설명하면?

OT 가용성을 고려해 기존 스캐닝 방법의 한계를 분석하고, 수동적 트래픽으로 장치를 식별하기 위한 특징과 머신러닝 연구 방향을 정리한 연구다.

### 머신러닝 측면의 핵심은?

프로토콜, 패킷 속성, 통신 행위라는 세 범주로 특징을 이해하고, IoT에서 유효했던 특징이 OT에서도 일반화되는지 검증할 필요를 정리한 것이다.

### 주기성만으로 장치를 식별할 수 있나?

일부 장치에서 도움이 될 수 있지만, 통신 상대·운영 상태·네트워크 조건에도 영향을 받는다. 다른 특징과 결합하고 현장·장치·시점을 분리한 검증이 필요하다.

### 신규 장치도 자동으로 알아내나?

알려진 종류의 새 개체를 분류하는 것과 처음 보는 종류를 미지로 처리하는 것은 다르다. 후자는 일반 분류 정확도 외에 별도의 설계와 평가가 필요하다.

### 이 논문에서 새 모델의 성능을 검증했나?

이 논문의 중심은 비교 조사와 연구 방향 제시다. 소개한 높은 정확도는 인용한 선행연구의 결과이며, 우리 모델의 측정 성과로 말하지 않는다.

## 14. 다시 볼 핵심

1. **OT 장치 식별은 취약점 관리의 출발점이며 가용성도 고려해야 한다.**
2. **수동적 관측은 추가 탐색 부담을 줄이지만, 보이지 않는 트래픽까지 식별하지는 못한다.**
3. **트래픽 특징은 프로토콜·패킷 속성·통신 행위로 나눠 생각할 수 있다.**
4. **TTL, IAT, CLRT는 서로 다른 정보를 나타낸다.**
5. **IoT 연구의 특징과 정확도를 OT 환경에 그대로 옮겨 주장하면 안 된다.**
6. **알려진 종류의 새 장치와 미지 유형을 구분해서 평가해야 한다.**
7. **무작위 패킷 분할보다 장치·세션·시간·현장 분리를 고민해야 한다.**
8. **논문의 성과는 비교 분석과 연구 과제 도출이며, 내 참여는 자료조사와 머신러닝 분석 중심이다.**
