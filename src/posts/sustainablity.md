## 1. 이 연구에서 해결하려던 문제

악성 앱 탐지 모델을 만들 때 높은 정확도를 얻는 것만으로는 충분하지 않다. **오늘 잘 맞는 모델이 몇 년 뒤에도 잘 맞을까? 새로운 데이터가 들어올 때마다 감당할 만한 비용으로 갱신할 수 있을까?**

내가 진행한 연구는 이 두 질문에서 출발했다. 안드로이드 앱의 특성이 시간에 따라 바뀌는 환경에서, 탐지 성능을 유지하면서 모델 갱신 비용을 줄이는 것이 목표였다.

핵심 아이디어는 다음과 같다.

> 앱이 어느 시기의 특성과 가까운지 먼저 추정하고, 그 확률을 가중치로 사용해 연도별 악성코드 탐지 모델의 판단을 합친다.

| 구분 | 핵심 내용 |
| --- | --- |
| 문제 | 시간이 지나면서 기존 모델의 탐지 성능이 떨어지는 Model Aging |
| 비교 방식 | 누적 데이터 전체 재학습, Random Forest의 warm start 기반 갱신 |
| 제안 방식 | 연도 예측 모델 + 연도별 악성코드 탐지 모델 + 확률 가중 투표 |
| 데이터 | 2014–2022년 108,000개, 2023년 테스트 전용 6,000개 |
| 기반 알고리즘 | Random Forest |
| 주요 결과 | 전체 재학습에 가까운 탐지 성능을 유지하면서 갱신 학습 비용 감소 |
| 대표 수치 | 2022년 학습 시간 68,272.24ms → 5,915.93ms, 약 11.5배 차이 |
| 함께 봐야 할 비용 | 여러 연도별 모델을 실행하므로 예측 시간은 비교 방식 중 가장 길었음 |

이 글은 IEEE Access에 게재한 **Enhancing the Sustainability of Machine Learning-Based Malware Detection Techniques for Android Applications**를 바탕으로 연구 설계와 결과를 다시 정리한 노트다. 수치와 실험 결과는 논문 보고값이며, 이 글에서 실험을 새로 재현한 것은 아니다.

## 2. 배경: 모델은 왜 시간이 지나면 성능이 떨어질까?

### 2.1 Concept Drift와 Model Aging

머신러닝 모델은 학습 데이터에서 입력 특징과 정답의 관계를 배운다. 그런데 실제 환경에서는 앱을 만드는 방식, 사용하는 API, 안드로이드 플랫폼, 악성 행위의 구현 방식이 계속 바뀐다.

예를 들어 과거에는 악성 앱을 구별하는 데 유용했던 API 사용 패턴이 이후에는 정상 앱에서도 흔해질 수 있다. 반대로 새로운 악성 앱이 과거 데이터에 거의 없던 패턴을 사용할 수도 있다.

| 용어 | 의미 | 이 연구에서의 맥락 |
| --- | --- | --- |
| 시간에 따른 분포 변화 | 시기마다 입력 데이터의 통계적 특성이 달라지는 현상 | 연도별 앱의 API·SDK 특성 변화 |
| Concept Drift | 엄밀하게는 입력과 정답의 관계가 변하는 현상. 넓은 맥락에서는 시간에 따른 변화 전반을 함께 논의하기도 함 | 과거에 학습한 탐지 기준이 이후 앱에 잘 적용되지 않는 문제 |
| Model Aging | 모델을 계속 사용하면서 성능이 저하되는 결과 | 과거 연도 모델의 미래 연도 탐지 성능 하락 |
| Sustainability | 변화하는 환경에서 성능과 유지 비용을 함께 감당할 수 있는 정도 | 높은 성능, 낮은 갱신 비용, 장기 운영 가능성 |

입력 분포가 달라졌다는 사실만으로 조건부 정답 분포까지 바뀌었다고 단정할 수는 없다. 이 연구에서는 연도 간 탐지 성능 저하를 관찰하고, 시간적 변화에 대응하는 모델 구조를 설계했다.

### 2.2 실제로 관찰한 성능 저하

논문 Table 3은 한 해의 데이터로 학습한 모델을 다른 연도 데이터에 적용한 결과다. 아래는 그중 일부다. 표의 원래 값은 0–1 범위로 제시되어 있어 여기서는 백분율로 바꾸었다.

| 학습한 모델 | 테스트 연도 | 정확도 |
| --- | --- | ---: |
| 2014년 모델 | 2014 | 98% |
| 2014년 모델 | 2015 | 92% |
| 2014년 모델 | 2018 | 71% |
| 2014년 모델 | 2019 | 27% |
| 2014년 모델 | 2022 | 21% |
| 2019년 모델 | 2019 | 98% |
| 2019년 모델 | 2022 | 97% |

**같은 모델이라도 어느 시기의 앱을 검사하느냐에 따라 성능이 크게 달랐다.** 특히 2014년 모델과 2019년 모델의 결과를 비교하면, 최신 연도를 잘 탐지하는 기준이 과거 모델과 상당히 다르다는 점을 볼 수 있다.

이는 모든 모델이 매년 일정하게 나빠진다는 뜻은 아니다. 가까운 연도끼리는 특성을 공유하기도 하고, 플랫폼 변화가 큰 시점에서는 성능이 급격히 달라질 수도 있다.

## 3. 기존 갱신 방식의 한계

### 3.1 전체 재학습: t_clf

새로운 연도 데이터가 생기면 과거 데이터를 모두 합쳐 새로운 모델을 학습한다.

```text
2014년: [2014]로 새 모델 학습
2015년: [2014 + 2015]로 새 모델 학습
2016년: [2014 + 2015 + 2016]으로 새 모델 학습
```

장점은 누적 데이터를 사용해 모델 전체를 다시 구성할 수 있다는 점이다. 실험에서도 전반적으로 높은 정확도와 F1을 보였다.

대신 데이터가 쌓일수록 재학습해야 할 양이 커진다. 이 연구에서는 학습 시간이 크게 증가했다. 다만 **시간이 반드시 지수적으로 증가한다는 이론적 결과를 제시한 것은 아니다.**

### 3.2 Warm start 기반 갱신: w_clf

기존 Random Forest의 트리를 유지하면서 새로운 데이터로 학습한 트리를 추가하는 방식이다.

```text
기존 트리 유지 + 새 연도 데이터로 만든 트리 추가
```

전체 모델을 처음부터 다시 만들지 않으므로 갱신 비용을 줄일 수 있다. 그러나 과거 트리도 계속 판단에 참여하므로, 오래된 패턴의 영향이 새로운 환경에서 불리하게 작용할 수 있다.

여기서 주의할 점은 `warm_start`가 기존 트리 내부를 새 데이터로 계속 수정하는 `partial_fit` 방식과 같지 않다는 것이다. 이 연구의 비교 대상은 **Random Forest에 트리를 추가하는 특정 갱신 방식**이다. 그 결과를 모든 온라인 학습·점진 학습 알고리즘의 성능으로 일반화해서는 안 된다.

### 3.3 두 방식 사이에서 찾은 설계 방향

| 질문 | 설계 방향 |
| --- | --- |
| 과거 탐지 모델을 매번 다시 학습해야 할까? | 연도별로 학습한 모델을 보관하고 재사용한다. |
| 오래된 모델을 항상 같은 비중으로 사용해야 할까? | 입력 앱에 따라 연도별 가중치를 다르게 준다. |
| 연도를 정확히 하나만 골라야 할까? | 여러 연도의 가능성을 확률로 남겨 둔다. |
| 고차원 악성코드 모델 전체를 다시 학습해야 할까? | 저차원 연도 예측 모델과 새 연도 탐지 모델만 갱신한다. |

## 4. 데이터와 특징 설계

### 4.1 데이터 구성

APK는 AndroZoo에서 수집했다.

| 기간 | 연도별 정상 앱 | 연도별 악성 앱 | 합계 | 사용 목적 |
| --- | ---: | ---: | ---: | --- |
| 2014–2022년, 9개년 | 6,000 | 6,000 | 108,000 | 학습·검증·평가 |
| 2023년 | 3,000 | 3,000 | 6,000 | 테스트 전용 |
| 전체 | 57,000 | 57,000 | **114,000** | 실험 전체 데이터 |

2023년 데이터는 이전 연도보다 확보 가능한 수가 적어 테스트에만 사용했다. 따라서 ‘2014–2023년 전체로 학습한 모델’이라고 설명하면 실제 실험과 달라진다.

### 4.2 정답 라벨은 어떻게 정했나?

두 단계 모델에는 서로 다른 정답이 필요하다.

| 학습 과제 | 정답의 근거 | 주의할 점 |
| --- | --- | --- |
| 연도 예측 | AndroZoo의 `DEX_DATE`에서 추출한 연도 | 앱스토어에 실제 게시된 날짜와 완전히 같은 개념은 아님 |
| 악성 여부 탐지 | `VT_DETECTION` 값 | 여러 백신 엔진의 탐지 결과를 이용한 실험상 라벨 |

악성 여부의 기준은 다음과 같다.

```text
VT_DETECTION >= 3 → 악성
VT_DETECTION <= 2 → 정상
```

이는 실험에서 사용한 운영상 기준이다. 탐지 수가 2 이하라고 해서 실제로 안전하다는 사실이 보장되는 것은 아니다. 연도 또한 `DEX_DATE` 기반 대리 지표이므로, ‘정확한 최초 출시 연도’를 직접 관측한 것으로 해석하지 않는다.

### 4.3 두 모델에 서로 다른 특징을 넣은 이유

| 구분 | 연도 예측 모델 y_clf | 악성코드 탐지 모델 v_clf |
| --- | --- | --- |
| 질문 | 어느 시기의 앱과 가까운가? | 정상인가, 악성인가? |
| 입력 | API Level 관련 특징 5개 | API Call 특징 1,848개 |
| 예시 | `minSdkVersion`, `targetSdkVersion`, `compileSdkVersion` 등 | DEX 코드에서 추출한 API 호출 정보 |
| 추출 대상 | `AndroidManifest.xml` | `classes.dex` |
| 추출 도구 | AAPT2 | DexDump |
| 학습 범위 | 2014년부터 현재 기준 연도까지 누적 | 해당 연도 데이터만 사용 |

설계의 요점은 **시대를 구분하는 문제에는 가벼운 특징을 사용하고, 악성 여부를 판단하는 문제에는 더 풍부한 특징을 사용하는 것**이다.

SDK의 API Level과 API Call은 다른 개념이다. API Level은 SDK 버전과 관련된 메타데이터이고, API Call은 앱 코드가 참조하는 API 호출 정보다.

또한 이 연구의 API Call 특징은 APK를 분석해 얻는 정적 정보다. 실제 실행 중의 모든 행위를 관찰하는 동적 분석과 동일하게 보면 안 된다.

## 5. 제안 모델: yv_clf의 전체 구조

표기를 먼저 정리하면 구조가 훨씬 단순해진다.

| 표기 | 의미 |
| --- | --- |
| n | 현재까지 학습에 반영한 마지막 연도 |
| i | 개별 연도별 모델의 담당 연도 |
| y_clf_n | 2014–n년 데이터로 학습한 연도 예측 모델 |
| v_clf_i | i년 데이터만으로 학습한 악성코드 탐지 모델 |
| yv_clf_n | 연도 예측과 2014–n년 탐지 모델을 결합한 전체 시스템 |

### 5.1 추론 흐름

```text
입력 APK
  │
  ├─ SDK/API Level 특징 ─→ 연도 예측 모델 y_clf
  │                          │
  │                          └─ 연도별 확률 q_i
  │
  └─ API Call 특징 ──────→ 연도별 탐지 모델 v_clf_i
                             │
                             └─ 각 모델의 악성 점수 r_i

               최종 악성 점수 = Σ(q_i × r_i)
                             │
                             └─ 정상 / 악성 판단
```

연도 예측 모델은 **어느 연도 모델의 의견을 얼마나 반영할지**를 정한다. 연도별 탐지 모델은 **자신이 학습한 시기의 기준에서 악성 여부**를 판단한다.

이 구조는 입력에 따라 여러 전문가의 가중치를 정하는 혼합 전문가 구조와 유사하게 이해할 수 있다. 다만 이 논문은 Random Forest를 따로 학습해 결합한 방식이며, LLM이나 신경망을 공동 학습하는 모델은 아니다.

### 5.2 1단계: 연도를 하나로 확정하지 않는다

`y_clf`는 `predict_proba()`로 각 연도의 확률을 출력한다.

```text
2014년일 점수: 0.36
2015년일 점수: 0.50
2016년일 점수: 0.14
합계:          1.00
```

여기서 2015년이 가장 높다고 해서 다른 연도 모델을 모두 버리지 않는다. 앱이 인접 연도와 특성을 공유할 수 있고, 연도 예측도 틀릴 수 있기 때문이다.

### 5.3 2단계: 연도별 탐지 결과를 확률로 합친다

논문 Figure 3의 실제 설명용 예제를 계산해 보면 다음과 같다.

| 연도 | 연도 가중치 q_i | 해당 모델의 정상 점수 | 해당 모델의 악성 점수 r_i | 악성 점수 기여분 |
| --- | ---: | ---: | ---: | ---: |
| 2014 | 0.36 | 0.37 | 0.63 | 0.2268 |
| 2015 | 0.50 | 0.28 | 0.72 | 0.3600 |
| 2016 | 0.14 | 0.41 | 0.59 | 0.0826 |
| 합계 | 1.00 | — | — | **0.6694** |

```text
악성 점수 = 0.36×0.63 + 0.50×0.72 + 0.14×0.59
          = 0.6694 = 66.94%

정상 점수 = 0.36×0.37 + 0.50×0.28 + 0.14×0.41
          = 0.3306 = 33.06%
```

악성 점수가 정상 점수보다 높으므로 악성으로 판단한다. 정상·악성 중 하나씩만 고르는 다수결보다 각 모델의 판단 강도를 더 많이 반영하는 **확률 기반 가중 투표**다.

단, 66.94%는 모델이 산출한 결합 점수다. 실제 악성 비율과 정확히 일치하는 보정된 확률이라고까지 주장하려면 별도의 확률 보정·평가가 필요하다.

### 5.4 수식의 의미

```text
z(x): 앱 x의 SDK/API Level 특징
a(x): 앱 x의 API Call 특징

q_i(x) = 연도 예측 모델이 산출한 i년의 확률
r_i(x) = i년 탐지 모델이 산출한 악성 확률

s(x) = Σ q_i(x) × r_i(x)
       i = 2014, ..., n
```

직관적으로는 ‘그 연도일 가능성 × 그 연도 기준 악성 가능성’을 모두 더한다. 전체확률법칙과 닮은 형태지만, 실제 구현에서는 서로 다른 특징으로 학습한 모델의 추정값을 조합한다. 따라서 수식의 형태만으로 참인 확률을 정확히 복원한다고 보장되지는 않는다.

### 5.5 연도 예측을 틀려도 탐지가 맞을 수 있다

2015년 앱이 2014년으로 분류되더라도, 두 연도에서 악성을 구분하는 패턴이 비슷하면 최종 탐지는 맞을 수 있다.

논문 Table 7·8에서는 단일 연도를 선택하는 비교 방식도 확인했다.

| 실제 연도 → 예측 연도 | 해당 앱 수 | 선택된 연도별 모델의 악성·정상 분류 정확도 |
| --- | ---: | ---: |
| 2015 → 2014 | 1,221개 | 90.17% |
| 2016 → 2017 | 1,093개 | 96.34% |

이 수치는 해당 오분류 집단 안에서의 탐지 정확도다. 전체 데이터의 정확도나 연도 예측 정확도로 읽으면 안 된다.

단일 연도 예측의 평균 정확도는 약 0.51로 보고되지만, 이것이 전체 악성코드 탐지 정확도가 51%라는 뜻은 아니다. **중간 과제인 연도 맞히기와 최종 과제인 악성 탐지는 별도로 평가해야 한다.**

## 6. 새로운 해가 되면 무엇을 학습할까?

2016년까지 운영하던 시스템에 2017년 데이터가 추가된다고 생각해 보자.

| 구성 요소 | 갱신 방법 |
| --- | --- |
| v_clf_2014, v_clf_2015, v_clf_2016 | 기존 모델 유지 |
| v_clf_2017 | 2017년 데이터만 사용해 새로 학습 |
| y_clf_2017 | 2014–2017년의 누적 API Level 데이터로 다시 학습 |
| 최종 결합 | 연도 예측 확률과 네 개 연도별 탐지 모델을 연결 |

전체 재학습과의 차이는 과거의 고차원 악성 탐지 모델을 매번 다시 만들지 않는다는 데 있다. 누적 재학습은 특징 수가 적은 연도 예측 모델에 남겨 둔다.

따라서 이 방식은 ‘재학습이 전혀 없는 모델’이 아니다. **누적 재학습이 필요한 부분의 역할과 입력 차원을 줄인 모델**이라고 이해하는 것이 정확하다.

또한 학습 종료 연도가 2022년이라면 연도 예측 모델에는 2023년 클래스가 아직 없다. 2023년 앱이 들어오면 2014–2022년 모델들의 판단을 조합하며, 이후 2023년 데이터로 갱신해야 해당 연도 전문가를 추가할 수 있다.

## 7. 실험은 어떻게 설계했나?

### 7.1 공통 조건과 지표

세 방식 모두 Random Forest를 사용했다. 논문은 트리 수, 최대 깊이 등의 하이퍼파라미터를 조정하고 학습 과정에 5-fold 교차검증을 적용했다고 설명한다.

실험 환경은 Windows 10, Intel Core i5-12400 2.50GHz, RAM 32GB다. 따라서 실행 시간은 해당 환경에서 측정한 비교값이다.

| 지표 | 무엇을 보는가? | 해석할 때 주의할 점 |
| --- | --- | --- |
| Accuracy | 전체 앱 중 맞힌 비율 | 실제 악성 비율이 달라지면 체감 성능도 달라질 수 있음 |
| Precision | 악성이라고 경고한 앱 중 실제 악성 비율 | 정상 앱 오탐 부담과 연결됨 |
| Recall | 실제 악성 앱 중 찾아낸 비율 | 악성 앱 미탐과 연결됨 |
| F1 | Precision과 Recall의 조화평균 | 두 지표를 함께 보되 세부 오탐·미탐도 확인해야 함 |
| 학습 시간 | 모델 생성·갱신에 필요한 시간 | 추출·라벨링 등 전체 운영 비용과는 구별 |
| 예측 시간 | 모델로 분류하는 데 필요한 시간 | 처리량·지연 시간 평가와 연결됨 |
| 모델 파일 크기 | 저장 비용 | 상주 메모리 사용량과 동일하지는 않음 |

```text
TP: 악성 앱을 악성으로 탐지
TN: 정상 앱을 정상으로 탐지
FP: 정상 앱을 악성으로 오탐
FN: 악성 앱을 정상으로 미탐

Accuracy = (TP + TN) / (TP + TN + FP + FN)
Precision = TP / (TP + FP)
Recall = TP / (TP + FN)
F1 = 2TP / (2TP + FP + FN)
```

### 7.2 평가 A: 고정된 여러 연도 테스트셋

각 연도 데이터의 80%로 모델을 학습하고, 2014–2022년 각 연도의 나머지 20%를 평가에 사용한다. 연도별 지표의 평균으로 해당 학습 시점의 결과를 정리했다.

```text
예: 2016년까지 갱신한 모델

학습: 2014–2016년의 학습용 데이터
평가: 2014–2022년의 고정 테스트 데이터
```

연도별 테스트 데이터는 2,400개이며, 9개년 합계는 21,600개다. 같은 평가 대상을 유지하면서 누적 학습 범위가 넓어질 때 모델이 어떻게 달라지는지 비교한다.

여기에는 2016년 모델에 대한 2019년 평가처럼 **학습 시점보다 미래인 테스트 연도**도 포함된다. 이 결과를 ‘2016년의 실제 운영 성능’이나 ‘바로 다음 해의 성능’이라고 표현하면 안 된다. 논문 Figure 5·6이 이 평가에 해당한다.

### 7.3 평가 B: 다음 해를 맞히는 YoY 평가

학습 종료 연도를 n으로 두고, 바로 다음 해 n+1의 앱을 평가한다.

```text
2014년까지 학습 → 2015년 평가
2015년까지 학습 → 2016년 평가
...
2022년까지 학습 → 2023년 평가
```

새로운 앱이 유입되는 운영 상황에 더 가까운 시간 순서 평가다. 논문 Figure 10·11이 이에 해당한다.

이 그림의 가로축에서 2018년은 ‘2018년까지 학습한 모델’을 뜻하므로, 그 지점의 테스트 대상은 **2019년 앱**이다. 그래프를 읽을 때 학습 종료 연도와 테스트 연도를 구별해야 한다.

두 평가 모두 유용하지만 답하는 질문이 다르다. 고정 테스트셋 비교는 여러 시기에 걸친 성능 변화를, YoY 비교는 바로 다음 시기로의 일반화를 보여 준다.

## 8. 결과: 성능과 비용을 함께 보면 무엇이 달라지나?

### 8.1 탐지 성능

논문 전체 결과는 다음과 같이 해석할 수 있다.

| 방법 | 정확도·F1 경향 | 학습 비용 | 예측 비용 |
| --- | --- | --- | --- |
| 전체 재학습 t_clf | 전반적으로 높은 성능 | 누적 데이터가 커질수록 증가 | 비교 방식 중 낮음 |
| Warm start w_clf | 변화가 큰 구간에서 성능 열세 | 상대적으로 낮음 | 제안 모델보다 낮음 |
| 2단계 yv_clf | 전체 재학습에 가까운 높은 성능 | 전체 재학습보다 크게 낮음 | 비교 방식 중 가장 높음 |

핵심 성과는 모든 연도에서 모든 방법보다 높은 정확도를 얻었다는 것이 아니다. **전체 재학습에 가까운 탐지 성능을 더 낮은 갱신 학습 비용으로 유지하는 절충안을 제시한 것**이다.

### 8.2 학습 시간: 2022년 약 11.5배 차이

논문 Table 4의 학습 시간은 다음과 같다.

| 학습 종료 연도 | 전체 재학습 t_clf (ms) | Warm start w_clf (ms) | 2단계 yv_clf (ms) |
| --- | ---: | ---: | ---: |
| 2014 | 3,470.52 | 4,144.84 | 3,959.01 |
| 2015 | 7,909.49 | 4,092.62 | 4,177.37 |
| 2016 | 14,006.64 | 3,953.74 | 4,409.23 |
| 2017 | 20,336.19 | 3,407.74 | 4,440.19 |
| 2018 | 27,935.41 | 6,392.65 | 6,705.45 |
| 2019 | 37,511.46 | 4,194.77 | 4,781.10 |
| 2020 | 46,934.44 | 3,881.69 | 5,236.81 |
| 2021 | 59,572.76 | 5,022.57 | 6,412.38 |
| 2022 | **68,272.24** | **4,595.49** | **5,915.93** |

```text
2022년 전체 재학습 시간 / 2단계 모델 학습 시간
= 68,272.24 / 5,915.93
≈ 11.54
```

즉, 2022년의 제안 모델 학습 시간은 전체 재학습의 약 8.67%였다. 감소율로 표현하면 약 91.33%다. 이는 **해당 연도의 갱신 학습 시간 비교**이며, 전체 개발 과정이나 APK 분석 전체가 11.5배 빨라졌다는 뜻은 아니다.

Table 5에서는 2022년 제안 모델의 학습 비용을 다음과 같이 나눈다.

| 구성 요소 | 학습 시간 | 전체에서 차지하는 비중 |
| --- | ---: | ---: |
| 누적 연도 예측 모델 y_clf | 2,268.63ms | 38.35% |
| 새 연도 악성코드 탐지 모델 v_clf | 3,647.30ms | 61.65% |
| 합계 | 5,915.93ms | 100% |

연도 예측 모델은 누적 데이터로 재학습하므로 비용이 증가한다. 따라서 실험 구간에서 상대적으로 안정적이었다고 설명할 수는 있지만, 영원히 일정한 학습 시간이 보장되는 구조는 아니다.

### 8.3 예측 시간: 비용이 사라진 것은 아니다

Table 6의 2022년 예측 시간은 다음과 같다.

| 방법 | 보고된 예측 시간 |
| --- | ---: |
| t_clf | 611ms |
| w_clf | 1,993ms |
| yv_clf | 3,132ms |

제안 모델은 여러 연도별 탐지 모델을 실행하고 결과를 결합한다. 따라서 이 실험에서는 전체 재학습 모델보다 예측 시간이 약 5.13배 길었다.

이 값은 논문의 평가 작업에 대해 보고된 시간이다. APK 한 개당 지연 시간이 3,132ms라고 바꾸어 읽으면 안 된다.

학습 시간과 해당 예측 시간을 단순히 더하면 다음과 같다. 아래 합계는 논문 Table 4·6에서 직접 계산한 값이다.

| 방법 | 2022년 학습 + 보고된 예측 시간 |
| --- | ---: |
| t_clf | 68,883.24ms |
| w_clf | 6,588.49ms |
| yv_clf | 9,047.93ms |

이 조건에서는 제안 모델의 합계가 전체 재학습보다 작다. 그러나 실제 운영에서 모델을 한 번 갱신한 뒤 수많은 앱을 검사한다면 예측 비용의 비중이 훨씬 커질 수 있다.

```text
운영 비용을 볼 때의 기본 관점
= 갱신 횟수 × 갱신 비용
+ 처리하는 앱 수 × 앱당 예측 비용
+ 특징 추출·저장·라벨링 등 기타 비용
```

따라서 배치 검사와 실시간 검사에서 이 구조의 이점은 다르게 평가해야 한다.

### 8.4 모델 파일 크기

Figure 9에서는 실험 범위 내에서 제안 모델의 전체 파일 크기가 다른 방법과 비슷한 수준이었다. 다만 연도별 모델을 계속 추가하는 구조이므로, 장기간 운영해도 저장 비용이 늘지 않는다고 볼 수는 없다.

정리하면 이 연구에서 낮춘 것은 주로 **고차원 모델을 누적 데이터 전체로 다시 학습하는 비용**이다. 모델 수, 추론 비용, SDK 의존성까지 모두 제거한 것은 아니다.

## 9. 2019년 결과가 중요한 이유

두 평가에서 2019년을 읽는 방식이 다르다.

| 평가 | 관찰 | 의미 |
| --- | --- | --- |
| 고정 테스트셋 평가 | 2019년 데이터를 학습에 포함한 뒤 t_clf와 yv_clf의 성능이 크게 개선 | 변화한 시기의 데이터를 학습에 반영하는 효과 |
| YoY 평가 | 2018년까지 학습하고 2019년을 평가할 때 세 방식 모두 성능 하락 | 이전 시기 지식만으로 급격한 변화를 넘기 어려웠음 |

논문은 이를 2019년 전후 Android SDK 및 API 특성의 큰 변화와 연결해 설명한다. 두 관찰은 모순이 아니다. **변화를 겪기 전에는 대응이 어렵고, 변화 이후 데이터를 학습하면 회복할 수 있다**는 서로 다른 상황이다.

다만 정확히 어떤 SDK 변경이 성능 저하를 얼마나 일으켰는지를 분리한 인과 실험과는 구별해야 한다. 플랫폼 변화에 대한 논문의 해석을, 모든 원인을 입증한 결과로 확대하지 않는다.

이 지점은 제안 모델의 한계도 보여 준다. 연도별 모델을 결합하더라도, 모든 기존 전문가가 경험하지 못한 새로운 패턴에서는 성능이 떨어질 수 있다.

## 10. 연구의 의의와 내가 맡은 일

### 10.1 기술적 의의

첫째, 악성 탐지 성능만 비교하지 않고 학습 시간·예측 시간·저장 비용까지 함께 평가했다. 모델의 지속 가능성은 정확도 하나로 결정되지 않기 때문이다.

둘째, 입력 앱에 따라 과거 모델의 가중치를 다르게 부여했다. 오래된 모델을 무조건 버리거나 모든 모델을 같은 비중으로 합치는 대신 시간적 유사성을 활용했다.

셋째, 갱신이 필요한 부분을 분리했다. 고차원 연도별 탐지 모델은 재사용하고, 저차원 연도 예측 모델과 새 연도 탐지 모델을 갱신하도록 구성했다.

### 10.2 수행 범위

프로젝트에서는 데이터 수집부터 특징 추출, 모델 구성, 비교 실험과 결과 해석까지 핵심 파이프라인을 주도했다.

| 수행 단계 | 주요 내용 |
| --- | --- |
| 데이터 구축 | AndroZoo 기반 다년도 APK 수집, 연도·악성 라벨 구성, 전처리 |
| 특징 정형화 | APK의 SDK/API Level 정보와 API Call 정보 추출·정리 |
| 모델 설계 | 연도 예측기와 연도별 악성 탐지기를 결합한 2단계 구조 구성 |
| 결합 로직 | 연도별 확률을 가중치로 사용하는 확률 기반 투표 구현 |
| 실험 | 전체 재학습·warm start와 성능 및 비용 비교 |
| 결과 해석 | 연도 간 성능 차이, SDK 의존성, 추론 비용과 고도화 방향 분석 |

사용 기술은 Python, Scikit-learn, Pandas, NumPy, AndroZoo API와 APK 분석 도구다. 논문의 최종 특징 추출 설명은 AAPT2와 DexDump를 기준으로 한다.

연구 결과는 IEEE Access 논문 제1저자로 발표했다.

## 11. 한계: 어디까지 말할 수 있고 무엇이 남아 있나?

### 11.1 SDK 정보 조작에 취약할 수 있다

연도 예측 모델은 SDK 버전 정보를 사용한다. 공격자가 해당 필드를 조작하면 연도별 가중치가 부적절하게 정해져 최종 탐지에 영향을 줄 수 있다.

확률 가중 투표가 하나의 연도를 잘못 고르는 위험을 줄일 수는 있어도, SDK 특징 자체가 의도적으로 왜곡되는 문제까지 해결했다고 볼 수는 없다.

### 11.2 연도는 앱 특성을 나누는 근사 기준이다

같은 연도의 앱도 서로 다르고, 다른 연도의 앱이 유사한 구현 방식을 공유할 수 있다. 연도별 전문가가 유용하다는 결과와 연도가 최적의 분할 기준이라는 주장은 다르다.

또한 `DEX_DATE`가 실제 출시 시점과 어긋나거나 재패키징 등의 영향을 받는다면 연도 라벨에도 불확실성이 생긴다.

### 11.3 고정된 1,848개 API 특징의 한계

비교를 위해 동일한 특징 집합을 사용했지만, 시간이 지나면 새로운 API나 패턴이 중요해질 수 있다. 기존 특징 공간으로 표현되지 않는 변화는 모델을 갱신하는 것만으로 충분히 반영하기 어렵다.

### 11.4 모델 수와 추론 비용은 계속 관리해야 한다

매년 전문가가 늘면 모든 전문가를 실행하는 비용도 늘 수 있다. 연도 예측 모델의 누적 학습 비용도 증가한다.

논문은 오래된 모델 제거, 유사 모델 병합, 병렬 실행, 적응형 갱신 등을 향후 방향으로 제시한다. 이들은 완료된 성능 개선 결과와 구분해야 한다.

### 11.5 데이터셋과 실제 서비스는 다르다

이 연구 데이터는 정상과 악성을 1:1로 맞췄다. 실제 서비스의 악성 비율은 다를 수 있으므로 Precision, 오탐률, 미탐률을 운영 조건에 맞게 다시 확인해야 한다.

SHA 순서에 따라 수집한 표본이 실제 생태계를 완전히 대표한다고 보장할 수도 없다. 백신 기반 라벨의 불확실성, 유사 앱·재패키징 앱의 영향도 추가 검토 대상이다.

다음은 논문 결과를 실제 운영으로 확장할 때 별도로 확인할 항목이다.

- 학습·검증·테스트 사이 동일 APK 및 유사 앱 중복 여부
- 악성코드 패밀리나 앱 계열이 겹칠 때의 평가 편향
- 하이퍼파라미터 탐색과 최종 테스트셋의 분리
- 여러 난수 시드에서의 평균과 변동 폭
- APK 파싱 실패, 난독화, 누락 특징에 대한 처리
- 특징 추출·데이터 다운로드·라벨 확보를 포함한 전체 파이프라인 비용
- 실제 유입 비율에서의 오탐·미탐 및 확률 보정

이는 별도의 재검증 제안이며, 논문이 위 항목의 실패를 보였다는 뜻은 아니다.

## 12. 다음 연구로 확장한다면

### 12.1 SDK 대신 API 패턴 기반 클러스터링

논문에서 제시한 방향 중 하나는 앱을 API 호출 패턴이나 행위 관련 특징의 유사성으로 묶는 것이다.

```text
현재 구조
SDK 특징 → 연도 확률 → 연도별 전문가 결합

확장 방향
API/행위 특징 → 유사 앱 집단 → 집단별 전문가 선택 또는 결합
```

시간을 직접적인 분할 기준으로 쓰는 대신 앱 자체의 특성에 가까운 집단을 찾는다. SDK 메타데이터 의존성을 낮출 수 있지만, 클러스터의 안정성·갱신 비용·공격자 조작 가능성도 따로 평가해야 한다.

여기서 API 패턴 기반 클러스터링은 정적 특징으로도 가능하다. 이를 곧바로 동적 실행 분석을 구현했다는 의미로 사용하지 않는다.

### 12.2 전문가 수 줄이기

- **Pruning:** 활용도나 기여도가 낮은 과거 전문가 제거
- **Merging:** 유사한 시기·패턴의 전문가 통합
- **선택적 실행:** 가중치가 큰 일부 전문가만 실행
- **병렬화:** 독립적인 연도별 탐지 계산을 병렬 처리

일부 전문가만 실행한다면 제외한 확률 질량과 가중치 재정규화 방법까지 정해야 한다. 속도만 측정하지 말고 탐지 성능이 얼마나 바뀌는지도 함께 검증해야 한다.

### 12.3 Drift 감지와 갱신 시점 연결

연 단위로 무조건 갱신하는 대신, 분포 변화나 탐지 성능 저하 신호를 보고 갱신 시점을 정할 수 있다. 다만 실제 악성 라벨은 늦게 확보될 수 있으므로 입력 분포 변화와 정답 기반 성능 감시를 구별해야 한다.

### 12.4 특징과 가중치의 신뢰성 개선

연도별 특징 선택, 새로운 API 반영, 확률 보정, SDK 조작 실험을 함께 설계하면 모델의 약점을 더 구체적으로 확인할 수 있다.

이 항목들은 후속 연구 아이디어다. 현재 논문이 모두 구현·검증한 결과로 표현하지 않는다.

## 13. 질문으로 다시 정리하기

### 왜 최신 연도 모델 하나만 쓰지 않았나?

새로 유입되는 앱에도 오래된 SDK나 구현 패턴을 가진 앱이 있을 수 있다. 여러 시기 전문가를 입력별로 조합하는 방법을 탐색했다. 다만 최신 모델 단독 방식과의 우열은 동일 조건의 별도 비교가 있어야 확정할 수 있다.

### 왜 전체 재학습보다 비용이 낮아졌나?

과거의 고차원 악성 탐지기를 매번 다시 학습하지 않기 때문이다. 새 연도 탐지기는 새 연도 데이터만 사용하고, 누적 재학습은 5개 API Level 특징을 사용하는 연도 예측기에 남긴다.

### 연도 예측이 부정확한데도 왜 의미가 있나?

정확한 연도 자체보다 적절한 탐지 전문가에 가중치를 주는 것이 최종 목적이기 때문이다. 인접 연도의 탐지 모델도 비슷한 앱을 잘 분류할 수 있고, 확률 결합은 연도 추정의 불확실성을 남겨 둔다.

### 이 방식이 Concept Drift를 해결했나?

실험 범위에서 성능 저하를 완화하고 갱신 비용을 줄였다. 그러나 급격한 플랫폼 변화, 표현되지 않는 새 특징, SDK 조작까지 모두 해결한 것은 아니다.

### 가장 강조할 성과는?

전체 재학습에 가까운 탐지 성능을 유지하면서, 2022년 갱신 학습 시간을 약 68.27초에서 5.92초로 줄인 것이다. 동시에 예측 시간이 증가하는 비용을 확인했다.

### 다시 한다면 무엇부터 확인할까?

시간 순서와 중복 제거를 엄격히 통제한 평가, SDK 조작에 대한 강건성, 실제 유입 비율에서의 오탐·미탐, 갱신 사이 처리량에 따른 전체 비용을 우선 확인하고 싶다.

## 14. 기억해 둘 핵심

1. **모델은 시간에 따라 달라지는 데이터 앞에서 성능이 떨어질 수 있다.**
2. **전체 재학습은 성능이 좋지만 누적 갱신 비용이 커진다.**
3. **이 연구의 warm start는 기존 트리를 유지하고 새 트리를 추가하는 RF 갱신 방식이다.**
4. **제안 모델은 연도 확률로 연도별 탐지 모델의 악성 점수를 가중 합산한다.**
5. **누적 재학습을 없앤 것이 아니라 가벼운 연도 예측기로 분리했다.**
6. **2022년 학습 시간은 전체 재학습 대비 약 11.5배 짧았지만, 예측 시간은 더 길었다.**
7. **고정 테스트셋 평가와 다음 해 평가를 구분해야 한다.**
8. **SDK 의존성, 특징 노후화, 전문가 증가가 후속 과제다.**
